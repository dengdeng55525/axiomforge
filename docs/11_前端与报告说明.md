# 前端、报告与知识图谱说明

## 为什么内部保存 JSON

运行报告在服务端以 JSON 保存，是为了让运行可以回放、比较、审计和被 API/CLI 消费。JSON 是事实层，不等于用户界面。报告分为三层：

1. **结论层**：运行状态、质量门槛、选中候选、主指标、候选对比和交付建议，面向业务和答辩阅读。
2. **证据层**：规划依据、检查项、修复轨迹、资源观测、事件时间线，默认折叠，面向开发复盘。
3. **原始层**：完整 JSON、代码制品和 SHA256，面向审计、下载和自动化集成。

Streamlit 的“代码与报告”页默认展示结论层。中间 Agent 事件、规划、修复、资源和代码均可展开，下载区同时提供可打印 HTML、Markdown 和审计 JSON。服务端也提供 `/runs/{run_id}/summary`、`/report.html`、`/report.md` 和 `/report` 四种消费方式。

## 图谱不是布局图

知识库使用 SQLite 实现有向 property graph。节点和关系均持久化，图形布局只负责把它们画出来：

| 节点类型 | 含义 |
| --- | --- |
| TaskType / Capability | 任务类型与可复用能力卡 |
| Algorithm / Transform | 算法和数据变换 |
| DatasetVersion / Metric | 数据版本与评价指标 |
| Source / Environment | 公开来源和运行依赖 |
| ValidationRun / Artifact | 可复现验证运行与代码制品 |
| FailureExperience | 失败诊断和已验证修复经验 |

关系使用固定枚举，例如 `USES`（能力使用变换）、`REQUIRES`（前置依赖）、`EVALUATED_ON`（运行评测数据）、`MEASURED_BY`（运行使用指标）、`DERIVED_FROM`（经验来源运行）、`REPAIRS`（修复链）。每条关系可以保存 source、locator、run_id、版本或验证属性。

图检索先按任务类型和知识状态过滤，再从命中能力沿关系扩展最多两跳；返回 lexical score、graph score、evidence path 和 source locator。因而图谱会影响候选规划，同时保留了为什么命中的证据。UI 以节点类型颜色、关系中文标签和选中节点邻域解释这一结构，完整节点/边仍可导出 JSON。

## 生产使用边界

原型的 `passed` 表示通过当前固定数据协议、验证集和资源限制下的质量门槛，不代表可以绕过人工评审直接上线。封存测试集默认不计分，真实部署还需要业务数据回归、模型监控、漂移告警、权限和更强的 OS/容器沙箱。
