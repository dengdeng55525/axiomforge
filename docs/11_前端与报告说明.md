# 前端、报告与知识图谱说明

## 从需求到报告的界面

默认界面是 `web/` 中的 Vue 工作台，运行入口为 `http://127.0.0.1:8501/app/`，也可以使用 API 自带的 `http://127.0.0.1:8000/app/`。构建、启动与交互验收见 [交互工作台与参考设计](12_交互工作台与参考设计.md)。旧版 Streamlit 保留在 `ui/`，不再是默认入口。

创建任务时，用户先选择银行营销响应或短信分类数据协议，再选择 OpenAI API / 兼容 Responses 网关、DeepSeek API、本地 HTTP 或 Mock，并输入业务目标与约束。候选预算、修复、检索与消融设置收进高级设置；提交后直接进入该次运行的报告页。运行中页面读取实际事件和候选状态；终止、失败或缺少证据都作为独立状态展示。

历史列表可以按场景、状态、执行方式及关键词筛选，也可以复用历史需求创建新的运行。复用需求不会覆盖原始报告或原始代码。

## 为什么保留 JSON

运行报告在服务端以 JSON 保存，用于复现、审计和 API/CLI 消费。面向用户的报告分为三层：

| 层次 | 默认展示 | 可解决的问题 |
| --- | --- | --- |
| 结论 | 运行状态、选中候选、AP 与基线、候选比较、交付建议 | 本次生成了什么，验证结果如何 |
| 证据 | 四类验证摘要；逐项检查、代码、修复、来源、时间线和资源按需展开 | 为什么选择这个方案，哪些检查失败或缺失 |
| 原始记录 | 完整 JSON 默认折叠，提供下载 | 如何回放、核对、进行程序化处理 |

报告页不默认铺开 Agent 中间 JSON。用户可以打开可打印 HTML，下载 Markdown、JSON，或展开当前候选的代码并下载 `.py`。生成代码只读显示；浏览器不执行它。代码、修复诊断和来源证据随当前查看的候选切换，报告总览始终说明最终选中候选。

对应服务端接口为 `/runs/{run_id}/summary`、`/runs/{run_id}/report.html`、`/runs/{run_id}/report.md` 和 `/runs/{run_id}/report`。结构化原始报告继续保留原有字段，不为配合布局伪造事件、分数或完成百分比。

## 正确理解通过状态

`checks` 在实际报告中是检查对象列表，包含 `name`、`passed`、`mandatory` 和 `detail`。界面按这些真实记录汇总功能正确性、接口规范、运行稳定性和指标表现；缺少检查的组显示“检查未完整”或“尚无检查记录”，不判为通过。缺失指标显示空缺标记，不补零。

候选 `status=passed` 表示执行和强制检查通过；运行 `status=passed` 表示工作流选出了通过强制检查的候选并完成结果整理。**这不保证 AP 超过基线。** AP 比较是建议性门槛：

- `above_prevalence`：验证集 AP 高于类别占比基线。
- `baseline_or_worse`：验证集 AP 未超过该基线；仍可能同时出现 `status=passed`。
- `not_evaluated` 或缺失：质量状态显示为“待评估”。

Mock 会实际训练、预测和验证算法，代码生成采用固定规则。真实 API、Mock 与回放记录按持久化模式标记。全部指标属于验证集观测；封存测试集未参与候选选择或评分。界面结果进入代码审查与独立评估流程，生产上线需要补充业务验收。

## 图谱如何构建及参与检索

知识库使用 SQLite 持久化有向属性图。实际 schema 是 [runtime_schema.sql](../knowledge/runtime_schema.sql)，画布只呈现已存节点和关系。

| 节点类型 | 含义 |
| --- | --- |
| TaskType / Capability | 任务类型与带版本的能力卡 |
| Algorithm / Transform | 算法和数据处理方法 |
| DatasetVersion / Metric | 数据版本与评价指标 |
| Source / Environment | 可定位的知识来源和依赖环境 |
| ValidationRun / Artifact | 验证运行与代码制品 |
| FailureExperience | 失败诊断，以及拟议或验证过的修复经验 |

`USES` 连接能力与使用的方法，`REQUIRES` 表示依赖，`DERIVED_FROM` 表示来源，`EVALUATES` 连接运行与制品，`IMPLEMENTS` 表示制品参考的能力，`REPAIRS` 保存修复链，`SUPERSEDES` 保存能力版本关系。来源、哈希和验证字段按实际关系类型存储。

来源摄取会保存 URI、revision、哈希、定位信息，并从源码 AST 提取函数及依赖；能力卡另存输入输出、前置条件、依赖和证据。能力卡先经过结构检查，再通过运行结果和验证过的修复经验补充语义证据；算法有效性依据完整验证路径判断。

实际检索先按任务与知识状态过滤，再进行中英文词项匹配和最多两跳的关系扩展，记录文本分数、图加分与来源路径。当前检索实现采用可追溯的词项与图结构方法；语义向量检索列入后续扩展。

## 如何交互查看图谱证据

知识探索页包含“知识图谱”和“能力库”两个视图。图谱左侧为全局类型与关系图例，中间为可拖拽、缩放的 D3 画布，右侧为所选节点详情。点击选中不自动改变探索中心；“聚焦此节点”才切换到对应的一跳或两跳邻域。

支持节点类型、关系和文本过滤。关系过滤改变可遍历路径，节点类型及关键词过滤决定展示节点；中心节点保留以便定位。页面显示已返回数量、筛选隐藏数量和因上限省略的数量，不将局部图当作完整知识库。

`GET /graph/explore` 保留原有 `nodes/edges` 结构，补充全局图例、统计、所选中心和来源证据。默认上限为 120 节点、300 条边，最多允许 500 节点、1500 条边；当前画布请求 80 节点、160 条边。计数由完整数据库图快照计算后截取，适合本题的小型原型，不宣称数据库分页能力。原始 `GET /graph` 仍可用于导出。

`GET /capabilities/{capability_id}?version=N` 可查看指定不可变版本及哈希。详情中的来源定位、关联制品、实际验证运行及关联路径均取自持久化数据。报告指标注明所属运行和选中候选；关联验证不能自动变成当前能力的语义通过证明。来源全文与代码正文不会混入图谱概览。

## 交付与部署边界

当前是本地单用户原型。API 密钥只由后端读取，页面不接收密钥；本地 14B/四卡模型属于独立部署计划，连通性和吞吐以目标机器验收报告为准。执行器采用受限 AST 构造器及资源限制子进程；业务上线需要独立数据评估、阈值确认、运行监控和相应部署能力。
