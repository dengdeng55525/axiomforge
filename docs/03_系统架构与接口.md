# 系统架构、知识图谱与 Agent 合约

本文件描述 AlgoForge 的运行架构、角色合约、知识图谱和验证机制。工具选择与接入方式见 [技术选型与框架集成](14_技术选型与框架集成.md)，验收记录见 [实现与验收对照](08_实现与验收对照.md) 与 [前端验证索引](research/frontend_validation.json)。

## 1. 三层边界

~~~mermaid
flowchart LR
  U[自然语言 / CLI / Web] --> A[应用服务与 TaskSpec]
  A --> O[状态机与预算控制]
  O --> LC[LangChain RunnableSequence 角色链]
  K[(SQLite 能力图与版本)] --> R[StructuredTool 只读证据检索]
  R --> P[Planner]
  LC --> P
  P --> C[Coder]
  C --> S[静态检查]
  S --> W[资源限制子进程]
  W --> E[可信验证器]
  E --> V[Reviewer]
  V -->|有限修复| C
  E --> M[Memory Curator]
  M --> K
  E --> H[报告与制品]
  P --> L[LLMProvider / Endpoint Router]
  C --> L
  V --> L
  L --> G[OpenAI Responses / DeepSeek / 1–4 GPU vLLM]
~~~

控制层通过 LangChain Core 的角色链与检索工具连接任务阶段，并负责预算、状态和事实记录；模型层通过 OpenAI SDK Responses、DeepSeek HTTP 或本地 HTTP Provider 生成结构化建议与受限构造；执行层在资源限制子进程中产生真实预测。执行范围由受限 AST 构造语言定义，GPU 推理服务处理模型请求，算法 worker 只接收任务数据与模型构造计划。

## 2. 核心数据对象

| 对象 | 关键字段 | 校验约束 |
|---|---|---|
| TaskSpec | task_type、dataset_id、positive_label、feature_names、numeric_features、categorical_features、seed、primary_metric、feature_policy、limits | 任务和数据白名单；指标存在；预算为正；禁用字段不可恢复 |
| Source | source_id、uri、revision、content_sha256、license、locator | 文件哈希固定；路径不能逃逸；引用必须存在 |
| Capability | capability_id、version、input_schema、output_schema、preconditions、dependencies、evidence、status | 版本不可覆盖；出处与已验证运行双向追踪 |
| CandidatePlan | candidate_id、algorithm、variant、rationale、evidence_ids、parent_id | 算法与变体白名单；候选 ID 唯一；知识引用必须存在 |
| CodeArtifact | artifact_id、candidate_id、path、sha256、attempt、parent_artifact_id、capability_ids | 制品绑定运行与尝试；哈希标识代码；生成器不得改验证器 |
| RunReport | run_id、status、provenance、warnings、candidates、events、agent_trace；候选中含 checks、metrics、resources | 指标只由可信 evaluator 写入；失败不得写为 0 分伪成功；观测投影只读取已发生事件 |
| FailureExperience | failure_id、fingerprint、run_id、error_type、diagnosis、fix、task_type、validated、status | 诊断绑定原运行；验证状态由实际修复结果判定 |

### TaskSpec 示例

~~~json
{
  "task_type": "tabular_binary_classification",
  "dataset_id": "bank",
  "feature_policy": "precontact_conservative_v1",
  "positive_label": "yes",
  "feature_names": ["age", "job", "marital", "education", "default", "housing", "loan", "pdays", "previous", "poutcome"],
  "numeric_features": ["age", "pdays", "previous"],
  "categorical_features": ["job", "marital", "education", "default", "housing", "loan", "poutcome"],
  "seed": 42,
  "primary_metric": "average_precision",
  "limits": {"cpu": 2, "memory_mib": 2048, "timeout_s": 120}
}
~~~

示例对应运行报告的 `task_spec`。数据版本与切分记录在 `provenance.dataset.dataset_id` 和 `provenance.dataset.split_policy`；候选数与修复上限属于 `RunRequest`。传给生成构造器的上下文由 `datasets.public_task_spec` 提取，只包含任务类型、特征列表、正类标签和随机种子。

完整候选依赖从预安装清单选择，LLM 请求不包含安装权限。模型输出 JSON 经 schema 校验后再执行；格式错误记录为 `RESPONSE_SCHEMA_REJECTED`，纠正重试一次后仍无效则抛出结构化响应错误。必要阶段失败终止运行；可选 Beam 扩展失败的处理见第 6 节。

## 3. 知识图谱 schema

SQLite 持久化有类型的节点、边、来源和版本。`KnowledgeStore.search` 负责词项检索与有界图扩展；LangChain `StructuredTool` 提供带参数 schema 的只读调用入口。NetworkX 从图谱快照生成 Streamlit 布局，Vue 工作台使用 D3 呈现同一份节点与关系。

节点类型：TaskType、Capability、Algorithm、Transform、DatasetVersion、Metric、Environment、Source、Artifact、ValidationRun、FailureExperience。

主要边：

| 边 | 起点 → 终点 | 含义 |
|---|---|---|
| SOLVES | Capability → TaskType | 能力适用的任务 |
| IMPLEMENTS | Artifact → Capability | 代码实现哪个能力版本 |
| USES | Capability → Algorithm / Transform | 实现组合 |
| REQUIRES | Capability → Environment | 环境与依赖条件 |
| DERIVED_FROM | Capability / FailureExperience → Source / ValidationRun | 出处与经验来源 |
| EVALUATED_ON | ValidationRun → DatasetVersion | 验证的数据版本 |
| EVALUATES | ValidationRun → Artifact | 被测代码 |
| MEASURED_BY | ValidationRun → Metric | 指标及数值属性 |
| REPAIRS | Artifact → Artifact | 新代码修复哪个旧版本 |
| SUPERSEDES | Capability → Capability | 显式版本更新 |
| AVOIDED_BY | FailureExperience → Capability / Transform | 已验证的规避方法 |

边由 `source_id`、`target_id` 和 `relation` 唯一标识，扩展属性保存在 `properties_json`。各关系按需要记录 `origin`、`locator`、`value`、`validated` 或 `status`，分别表达来源、定位、指标值和验证事实。

运行数据库包含 `cf_sources`、`cf_nodes`、`cf_edges`、`cf_capability_versions`、`cf_runs`、`cf_run_revisions`、`cf_artifacts`、`cf_failures` 和 `cf_events`，定义见 [runtime_schema.sql](../knowledge/runtime_schema.sql)。`cf_edges.source_id/target_id` 外键引用 `cf_nodes.node_id`；运行快照按 `run_id + content_sha256` 去重并保留 revision，制品绑定运行、候选、执行尝试和代码哈希。能力内容哈希用于去重，稳定能力 ID 与递增版本共同保留演化历史。

运行报告中的 `agent_trace` 是由 [observability.py](../src/capability_factory/observability.py) 生成的派生视图，包含 `framework`、`spans`、`budget`、`evidence` 和脱敏 `events`。它遵循 `schema_version=1.0`，完整投影的 `cursor_sequence` 指向最后一个有效事件；通过游标读取时只保留 `sequence <= through_sequence` 的事实。历史报告缺少 Agent span 时，投影兼容 `LLM_RESPONSE`、`MOCK_RESPONSE` 和 `KNOWLEDGE_RETRIEVED`，缺少框架、预算或结束时间时返回 `null`。

status 不混用：draft / extracted / verified / deprecated 是知识状态；queued / running / passed / failed / cancelled 是运行状态。验证失败也入库，但不能出现在“已验证能力”的默认候选列表中。

### 一个真正用到图的检索例子

输入“表格二分类、类别未知、只允许 CPU、预算 120 秒”。先按任务类型和 extracted / verified 能力状态过滤最新版本，再做词项相关性检索，沿 USES、REQUIRES、AVOIDED_BY 展开最多两跳，并排除通用环境依赖产生的弱关联。返回的能力卡携带来源定位、词项分数、图分数和证据路径；来源关系 DERIVED_FROM 用于追溯知识出处。特征白名单、CPU 和运行时限由独立任务协议与预算控制执行。

每张返回的能力卡包括 matched_constraints、evidence_path、source_locator 和 rejected_reason；lexical_score 与 graph_score 分别记录词项和图扩展贡献。`--use-graph/--no-use-graph` 与 `--use-retrieval/--no-use-retrieval` 提供消融开关，可在相同任务和预算下比较图检索对方案、修复和验证结果的影响。

## 4. 多角色协作

| 角色 | 输入 | 输出 | 不允许的行为 |
|---|---|---|---|
| Extractor | 文档片段、AST 元信息、schema | 候选能力/关系与出处 | 自行执行来源代码；无出处事实直接入 verified |
| Planner | TaskSpec、证据包、历史错误 | 候选计划与理由 | 修改数据切分；用测试指标选模型 |
| Coder | 固定计划、接口、允许依赖 | model.py 或有限 diff | 修改 runner、评估标签或策略配置 |
| Reviewer | 代码、验证报告、计划与证据 | 分类诊断与有限修复指令 | 自行宣称测试通过或编造指标 |
| Memory Curator | 验证事实和已比较的补丁 | 有适用范围的经验候选 | 将未验证猜测当作普遍规律 |

一次运行选择一个 Provider，由对应模型承担不同角色。每个角色拥有独立提示词、输入输出契约与可观察交互。LangChain `RunnableSequence` 连接角色请求、Provider 生成与 Pydantic 输出校验；`StructuredTool` 在需求理解后提供只读图检索。状态机控制角色交接、预算、修复次数和候选选择。角色协作可以通过错误定位、修复成功率及 `multi_role` / `single_shot` 对照评测。

[agent_runtime.py](../src/capability_factory/agent_runtime.py) 将调用拆成 `invoke_provider → persist_response → validate_contract` 三步，保存响应后再校验结果；`CapabilitySearchInput` 为 `search_capabilities` 定义查询、任务类型、最多 6 条返回与图扩展开关。报告的 `provenance.agent_runtime` 保存框架版本、角色链、工具名与 `external_tracing=false`，`KNOWLEDGE_RETRIEVED.data.tool` 记录实际检索工具。外部 LangSmith 追踪通过 `tracing_context(enabled=False)` 关闭。

Agent 的自主范围限制为受控算法构建。业务约束、最终验证和发布门槛由确定性代码负责。

## 5. 工作流状态机

~~~text
RECEIVED → SPEC_VALIDATED → KNOWLEDGE_RETRIEVED → PLANNED
→ GENERATED → STATIC_CHECKED → EXECUTED → VERIFIED
  ├─ 合格 → COMPARED → RECORDED → COMPLETED
  ├─ 可修复且预算剩余 → DIAGNOSED → PATCHED → STATIC_CHECKED
  └─ 不可修复 / 超预算 → FAILED（保存报告和经验候选）
~~~

每次运行以 run_id 关联报告、候选和制品；事件保存 sequence、event_type、created_at 与 data。模型调用记录角色、请求模型、返回模型、提示词/响应哈希、耗时、token 用量和结束状态，候选计划保存 parent_id 与知识引用。界面展示决策依据、来源与工具结果，事件接口提供可复核的执行事实。

Agent 观测事件进一步记录角色和工具的生命周期：`AGENT_STARTED`/`AGENT_COMPLETED`/`AGENT_REJECTED`/`AGENT_FAILED` 表示结构化角色链边界，`TOOL_STARTED`/`TOOL_COMPLETED`/`TOOL_FAILED` 表示只读知识工具边界，`RUN_BUDGET_APPLIED` 与 `RUN_FINISHED` 表示运行级预算和终态。事件的 `data` 只携带白名单摘要，例如 schema、attempt、candidate_id、duration_seconds、returned_count、capability_ids 和 error_type。

停止条件：每候选最多两次修复、默认两个候选（可设为最多六个）、单候选 120 秒、整次任务 900 秒、LLM 调用最多 24 次；这些都是上限，任意预算先耗尽就终止。执行器保存实际超时和回收记录，不能只改变页面状态。

整次任务预算以表单/API 的 `max_seconds` 为上限。确定性解析器只接受原始需求中的明确数字时限，例如“整个任务最多运行 120 秒”或“Finish the run within 2 minutes”；取它与表单上限的较小值，最低 10 秒。未识别的表述应通过表单指定，数据中的通话时长和“2 models”等数字不会变成运行时限。解释器的 `requested_run_seconds` 保留用于审计，但不能独立修改截止时间；与可核验时限不一致时记录 `INTERPRETER_BUDGET_IGNORED`。`RUN_BUDGET_APPLIED` 和报告 `timing` 保存实际采用的时限。

HTTP Provider 对可重试的传输错误、限流和暂时服务错误设置有限重试；每次重试都受当前运行预算约束。鉴权和参数错误形成明确的 Provider 异常。Mock 是独立选择的测试模式，报告通过 provider 与 mode 字段记录实际运行路线。

## 6. 有界 Beam Search

首层生成两个完整可执行方案，例如 LR 与 RandomForest。每个方案评估后各扩展最多两个合法变化，形成第二层最多四个节点。beam width=2，最大深度=2，完整评估节点总计最多六个。

扩展数同时受剩余候选预算、全局唯一 `(algorithm, variant)` 和每父节点最多两个子节点约束。两个逻辑回归父节点若已使用 `default` 和 `balanced`，则只剩一个 `regularized` 变体，规划器只会被要求生成一个子节点。多个父节点可提供同一变体的来源选项，但这些选项不重复计入容量；Mock 和 HTTP 路径使用相同的计划校验。

可选扩展经有限纠正仍违反 schema 或计划合约时，记录 `BEAM_SKIPPED` 并保留已通过验证的父候选，继续比较、报告和知识回写。报告必须展示该警告，不能声称跳过的节点已执行。服务故障、超预算和必要阶段失败仍保留失败终态。

同一轮全部候选使用相同数据、特征协议和资源预算。先筛选通过强制检查的候选，再按 validation AP 降序排列；AP 相同时按候选 wall_seconds 升序排列。报告额外展示 AP、训练时间和峰值 RSS 的 Pareto 前沿以及父子方案变化，说明质量与资源取舍。

搜索记录保存候选父子关系、方案、验证指标、资源与剪枝理由，形成可查看的扩展与选择轨迹。项目选择 Beam Search 适配当前有限算法变体空间，以候选上限、深度和运行预算控制搜索成本。

## 7. 算法插件与生成代码边界

生成代码实现 `build_pipeline(task_spec)`，使用允许的 scikit-learn 构造器返回具备 `fit` 与 `predict_proba` 的 Pipeline。trusted runner 负责读取划分、调用训练、执行推理和序列化输出，可信 evaluator 管理验证标签与指标计算。

插件入口由 [plugins.py](../src/capability_factory/plugins.py) 提供。下面在当前应用进程注册一个额外指标，后续验证会将结果写为 `plugin_brier_loss`：

~~~python
from capability_factory.plugins import brier_loss, register_metric

register_metric("brier_loss", brier_loss)
~~~

指标通过 `register_metric(name, function)` 注册，参考构造模板通过 `register_template(task_type, algorithm, function)` 注册；模板仍须通过同一 AST 与依赖白名单。注册在应用启动阶段、首次运行之前执行，同名重复注册会报错。表格和 SMS 任务共享工作流，各自使用对应数据协议与模板；插件由维护者显式注册，完整步骤见 [插件扩展指南](10_插件扩展指南.md)。

预测输出至少包含 row_id、positive_class、score；严格检查唯一行号、长度、顺序、有限值、[0,1] 区间和类别映射。不能默认 predict_proba 第二列永远是正类。

## 8. 安全执行与验证信任边界

当前实现：先检查文件名、语法、允许 import、危险调用、大小限制和依赖清单，再由受限构造器创建获准的 scikit-learn Pipeline。算法在独立子进程中运行，施加 CPU、内存和时间限制；可信 evaluator 只接收受长度限制的预测结果，不在宿主进程加载生成的 pickle/joblib。

执行层采用受限 AST 构造器与资源限制子进程。公网部署需要专用执行节点、强化运行时、凭证边界、认证、租户隔离和审计配置；任意用户代码接入需要单独的安全评估。

模型凭证只由 API worker 使用，不传给算法 worker。安全/接口检查失败时，即使指标较高也不能显示为可交付；质量门槛和强制检查在报告中分开记录。

## 9. API / CLI / UI 规格

API：POST /runs、GET /runs/{id}、GET /runs/{id}/events、GET /runs/{id}/report、GET /runs/{id}/artifacts、POST /runs/{id}/cancel、GET /capabilities、GET /health。运行请求通过 provider 选择 `openai`、`deepseek`、`local_http` 或 `mock`；OpenAI 模式使用官方 Python SDK 调用配置端点的 Responses API，网关与官方服务身份按实际 base_url 记录。

观测接口：`GET /runs/{id}/agent-trace` 返回当前完整 Agent 观测投影；追加 `through_sequence=N` 返回只包含游标之前事实的回放投影。接口不会重新执行角色、工具或验证器，非法游标会被 API 参数校验拒绝。投影字段、事件类型和前端交互见 [Agent 观测与回放](15_Agent观测与回放.md)。

POST /runs 接受自然语言、dataset_id 和有限配置；返回 run_id。不得接受任意服务器文件路径、任意 shell 命令或未校验 provider URL。LLM 地址由部署者设置，避免 SSRF。

默认 Vue 工作台提供六个页面：概览、创建任务、运行报告、知识探索、历史记录、模型与环境；旧版 Streamlit 仅作为兼容入口。运行中的耗时/预算、真实/回放/mock 模式应始终可见。

运行报告页面的 Agent 观测台展示角色 span、工具检索、调用预算、token 与时间消耗，并用折叠区承载事件详情；事件滑块将游标传给 `agent-trace` 接口，页面只显示已发生信息。

当前 CLI 已实现：`init`、`run`、`serve`、`doctor`、`report`、`export-graph`、`ingest-repo`、`analyze-run`、`export-openapi`。仓库抽取、资源分析和接口导出的复现步骤见 [加分项演示](13_创新点与加分项演示.md)。离线脚本 `scripts/export_graphml.py` 还可将同一 SQLite 图谱导出为 GraphML，供 Gephi、yEd、NetworkX 或 Neo4j 适配器复核，不需要 API 服务或模型凭证。

```bash
python -m capability_factory export-graph --output artifacts/graph.json
python scripts/export_graphml.py --database artifacts/knowledge.sqlite3 --output artifacts/graph.graphml
```

GraphML 的节点/边属性以 JSON 字符串保留嵌套 provenance 字段，原始 ID 同时写入
`original_id`，因此导出不会丢失来源定位。SQLite 仍是权威事实源；JSON 和 GraphML
都是可重新生成的交换制品。

## 10. 可复现与部署

应用与 LLM serving 分别锁依赖；vLLM 的 PyTorch/CUDA 环境不能污染 CPU 算法 worker。记录实际模型 revision、tokenizer、quantization、serving image digest、驱动版本、预算和并发。LLM temperature=0 也不保证跨硬件逐位一致，因此另外保留输入输出制品回放。

SQLite 开启外键与 WAL，每次操作使用独立连接，写入通过 `BEGIN IMMEDIATE` 事务串行协调并保持短事务；四个模型 endpoint 只返回推理结果，不直接写数据库。多机时不要把 SQLite 放网络文件系统共享写入；需要更高写并发再替换 Repository 接口为 PostgreSQL。
