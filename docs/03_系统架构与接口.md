# 系统架构、知识图谱与 Agent 合约

本文件是开发规格；除已标注的准备脚本外，以下模块仍待实现。

## 1. 三层边界

~~~mermaid
flowchart LR
  U[自然语言 / CLI / Web] --> A[应用服务与 TaskSpec]
  A --> O[状态机与预算控制]
  K[(SQLite 能力图与版本)] --> R[证据检索]
  R --> P[Planner]
  O --> P
  P --> C[Coder]
  C --> S[静态检查]
  S --> W[隔离 CPU Worker]
  W --> E[可信验证器]
  E --> V[Reviewer]
  V -->|有限修复| C
  E --> M[Memory Curator]
  M --> K
  E --> H[报告与制品]
  P --> L[LLMProvider / Endpoint Router]
  C --> L
  V --> L
  L --> G[API 或 1–6 GPU 推理服务]
~~~

控制层负责预算、状态、授权与事实记录；模型层生成结构化建议与代码；执行层在隔离环境产生真实预测。三层不共享任意宿主机文件访问权。GPU 推理服务不运行生成的算法代码，算法 worker 不持有 API 密钥。

## 2. 核心数据对象

| 对象 | 必需字段 | 校验约束 |
|---|---|---|
| TaskSpec | id、task_type、dataset_version、target、positive_label、feature_policy、split_id、metrics、limits | 任务和数据白名单；指标存在；预算为正；禁用字段不可恢复 |
| Source | source_id、uri、revision、content_sha256、license、locator | 文件哈希固定；路径不能逃逸；引用必须存在 |
| Capability | capability_id、version、input_schema、output_schema、preconditions、dependencies、evidence、status | 版本不可覆盖；出处与已验证运行双向追踪 |
| Plan | plan_id、parent_id、algorithm、preprocessing、parameters、citations、budget | 算法与依赖允许；证据支持选择；有预算估算 |
| CodeArtifact | artifact_id、source_hash、parent_artifact_id、files、dependency_lock_hash | 文件白名单；哈希不变；生成器不得改验证器 |
| VerificationReport | run_id、checks、metrics、resources、warnings、status、provenance | 指标只由可信 evaluator 写入；失败不得写为 0 分伪成功 |
| FailureExperience | fingerprint、symptom、root_cause、proposed_fix、scope、validation_runs、status | 猜测与实证分开；适用版本明确 |

### TaskSpec 示例

~~~json
{
  "task_type": "tabular_binary_classification",
  "dataset_id": "uci-bank-additional-full",
  "feature_policy": "precontact_conservative_v1",
  "target": "y",
  "positive_label": "yes",
  "primary_metric": "average_precision",
  "split_id": "ordered_60_20_20_v1",
  "limits": {"cpu": 2, "memory_mib": 2048, "timeout_s": 120},
  "max_repairs": 2,
  "max_candidates": 6
}
~~~

完整候选依赖必须从预安装清单选择；不能让 LLM 任意运行 pip install。模型输出 JSON 经 schema 校验后再执行；解析失败是可识别的格式错误，最多重试两次，仍失败则进入终态。

## 3. 知识图谱 schema

使用 SQLite 存储有类型的节点和边；NetworkX 只从权威库生成视图。

节点类型：TaskType、Capability、Algorithm、Transform、DatasetVersion、Metric、Environment、Source、Artifact、ValidationRun、FailureExperience。

主要边：

| 边 | 起点 → 终点 | 含义 |
|---|---|---|
| SOLVES | Capability → TaskType | 能力适用的任务 |
| IMPLEMENTS | Artifact → Capability | 代码实现哪个能力版本 |
| USES | Capability → Algorithm / Transform | 实现组合 |
| REQUIRES | Capability → Environment | 环境与依赖条件 |
| DERIVED_FROM | Capability / FailureExperience → Source / ValidationRun | 出处与经验来源 |
| EVALUATED_ON | ValidationRun → DatasetVersion | 验证的数据版本 |
| EVALUATES | ValidationRun → Artifact | 被测代码 |
| MEASURED_BY | ValidationRun → Metric | 指标及数值属性 |
| REPAIRS | Artifact → Artifact | 新代码修复哪个旧版本 |
| SUPERSEDES | Capability → Capability | 显式版本更新 |
| AVOIDED_BY | FailureExperience → Capability / Transform | 已验证的规避方法 |

边属性包括 relation_version、source_id、confidence、valid_from、适用 task/environment，以及人工/抽取/运行产生的 origin。

数据库至少包含：sources、nodes、edges、capability_versions、runs、artifacts、failures、events、schema_migrations。关系表的 source_node_id/target_node_id 设置外键；运行结果按 run_id + artifact_hash 幂等写入。内容哈希用于去重，但能力 ID 与业务版本独立。

status 不混用：draft / extracted / verified / deprecated 是知识状态；queued / running / passed / failed / cancelled 是运行状态。验证失败也入库，但不能出现在“已验证能力”的默认候选列表中。

### 一个真正用到图的检索例子

输入“表格二分类、类别未知、只允许 CPU、预算 120 秒”。先根据任务与硬约束过滤节点，再做文本相关性检索，沿 USES、REQUIRES、DERIVED_FROM、AVOIDED_BY 展开最多两跳。返回概率接口、混合列处理、未知类别容错以及有关 sparse/dense 不兼容的历史经验。只返回与当前版本兼容的验证记录。

每个候选输出 matched_constraints、evidence_path、source_locator 和 rejected_reason。主证据不靠漂亮的图，而靠“若去掉这条关系，生成或验证会发生什么变化”的消融结果。

## 4. 多角色协作

| 角色 | 输入 | 输出 | 不允许的行为 |
|---|---|---|---|
| Extractor | 文档片段、AST 元信息、schema | 候选能力/关系与出处 | 自行执行来源代码；无出处事实直接入 verified |
| Planner | TaskSpec、证据包、历史错误 | 候选计划与理由 | 修改数据切分；用测试指标选模型 |
| Coder | 固定计划、接口、允许依赖 | model.py 或有限 diff | 修改 runner、评估标签或策略配置 |
| Reviewer | 代码、验证报告、计划与证据 | 分类诊断与有限修复指令 | 自行宣称测试通过或编造指标 |
| Memory Curator | 验证事实和已比较的补丁 | 有适用范围的经验候选 | 将未验证猜测当作普遍规律 |

同一个 LLM 可以承担不同角色，但必须具有独立上下文、输入输出契约与可观察交互，不只是一次提示词里写几个角色名称。角色协作的价值通过错误定位质量、二轮修复成功率和消融体现，不能以调用次数代替效果。

Agent 的自主范围限制为受控算法构建。业务约束、最终验证和发布门槛由确定性代码负责。

## 5. 工作流状态机

~~~text
RECEIVED → SPEC_VALIDATED → KNOWLEDGE_RETRIEVED → PLANNED
→ GENERATED → STATIC_CHECKED → EXECUTED → VERIFIED
  ├─ 合格 → COMPARED → RECORDED → COMPLETED
  ├─ 可修复且预算剩余 → DIAGNOSED → PATCHED → STATIC_CHECKED
  └─ 不可修复 / 超预算 → FAILED（保存报告和经验候选）
~~~

所有步骤有结构化事件：run_id、step_id、parent_id、role、provider、model_revision、prompt_version、输入输出哈希、耗时、token 数、结束原因。不给用户展示隐藏思维链，只展示简明的决策依据、来源与工具结果。

停止条件：每候选最多两次修复、默认六个不同候选、单候选 120 秒、整次任务 900 秒、LLM 调用最多 24 次；这些都是上限，任意预算先耗尽就终止。超时必须回收进程/容器与 GPU 请求租约，不能只改变页面状态。

API 超时和限流按可重试错误处理；401/参数不合法不反复重试。指数退避有全局上限。provider 故障不能悄悄退回 mock 并仍标为真实成功。

## 6. Beam Search：做小但做实

首层生成两个完整可执行方案，例如 LR 与 RandomForest。每个方案评估后各扩展最多两个合法变化，形成第二层最多四个节点。beam width=2，最大深度=2，完整评估节点总计最多六个。

同一轮全部候选使用相同数据、特征协议和资源预算。先做硬门槛过滤，再按 validation AP 排序；AP 接近时优先更低资源消耗、结构更简单的方案。若采用不同样本规模的快速预筛，必须单独标注 fidelity，不得把低/高保真分数混排。

保留 parent、mutation、evidence、hard_gate_status、metric、cost、pruned_reason。最终可视化是一棵真正有扩展和剪枝的搜索树。暂不实现 MCTS：小候选空间中其工程成本难以换来可信的额外收益。

## 7. 算法插件与生成代码边界

首版生成代码仅实现 build_pipeline(task_spec) 和必要的纯转换器，返回有 fit 与 predict_proba 的对象；trusted runner 负责读取划分、调用训练、执行推理、序列化输出。这样仍有真实代码生成/修复，但不把标签和评估控制权交给生成器。

~~~python
class TaskPlugin(Protocol):
    def validate_input(self, frame, task_spec): ...
    def build_reference_baseline(self, task_spec): ...
    def checks(self, task_spec): ...
    def report_sections(self, report): ...

class LLMProvider(Protocol):
    async def generate(self, request, response_schema, budget): ...

class SandboxRunner(Protocol):
    def run(self, artifact, dataset_slice, limits): ...
~~~

注册表以 task_type 和 metric_name 查找插件。新增短信任务只增加文本插件、能力知识和配置，不改状态机。动态插件必须是维护者审核安装的代码，不从任意上传路径自动 import。

预测输出至少包含 row_id、positive_class、score；严格检查唯一行号、长度、顺序、有限值、[0,1] 区间和类别映射。不能默认 predict_proba 第二列永远是正类。

## 8. 安全执行与验证信任边界

阶段一：检查文件名、语法、允许 import、危险调用、大小限制和依赖清单。AST/关键词检查只能发现一部分风险，不能等同沙箱。

阶段二：生成代码只在独立 worker 容器执行。目标配置：非 root、只读根文件系统、禁网、删除 capabilities、no-new-privileges、默认 seccomp、进程数限制、CPU/内存/时间限制；输入只读挂载，输出只挂载本 run 的临时目录。不能挂宿主机根目录、SSH、.env、Docker socket 或最终测试标签。

阶段三：可信 evaluator 只接收受长度限制的 JSON/CSV 预测，不在宿主进程加载生成的 pickle/joblib，也不执行生成的测试脚本。保存模型可使用 sandbox 内 joblib，未来推理也在隔离容器内完成，不能将文件跨回主进程反序列化。

阶段四：系统安全与资源检查失败时，即使指标再高也不能发布。指标表现不达标与接口/安全失败分别标注，避免一个总分掩盖阻断问题。

Docker 是原型的隔离基础，不代表抵御所有恶意租户；若开放互联网任意用户代码执行，后续需专用节点、强化运行时或微虚机和更严的凭证边界。这是部署范围变化，不是当前笔试原型的必要依赖。

当前环境没有发现 Docker 命令。实现时先接入可用的独立 Linux 执行节点或安装可用运行时；若环境不允许，禁用不受信生成代码的执行能力。受信人工模板可用于离线测试，但报告必须写明 sandbox=unavailable，不能把普通 subprocess 宣传为安全沙箱。

## 9. API / CLI / UI 规格

API：POST /runs、GET /runs/{id}、GET /runs/{id}/events、GET /runs/{id}/report、GET /runs/{id}/artifacts、POST /runs/{id}/cancel、GET /capabilities、GET /health。

POST /runs 接受自然语言、dataset_id 和有限配置；返回 run_id。不得接受任意服务器文件路径、任意 shell 命令或未校验 provider URL。LLM 地址由部署者设置，避免 SSRF。

UI 只做四页：提交任务；实时步骤/候选；代码与验证报告；知识图与失败经验。运行中的耗时/预算、真实/回放/mock 模式应始终可见。

最终 CLI 目标：algoforge doctor、ingest、run、compare、report、export-graph。当前 README 只列出实际已实现的准备命令，不提前宣称这些目标命令可用。

## 10. 可复现与部署

应用与 LLM serving 分别锁依赖；vLLM 的 PyTorch/CUDA 环境不能污染 CPU 算法 worker。记录实际模型 revision、tokenizer、quantization、serving image digest、驱动版本、预算和并发。LLM temperature=0 也不保证跨硬件逐位一致，因此另外保留输入输出制品回放。

SQLite 开启外键，写入集中由一个 writer 执行，采用事务和短写操作；六个模型 endpoint 只返回推理结果，不直接写数据库。多机时不要把 SQLite 放网络文件系统共享写入；需要更高写并发再替换 Repository 接口为 PostgreSQL。
