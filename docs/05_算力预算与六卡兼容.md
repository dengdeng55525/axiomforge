# 算力、模型部署与 1–6 张 RTX 4090D 扩展

## 1. 先给结论

**2026-09-28 实施更新：当前使用 DeepSeek-V4.1-Flash API，模型 ID 为 deepseek-flash。
已实际完成银行与短信的真实 API 闭环，不需要本地 GPU 推理；暂不部署本地模型。**
单卡和未来最多六卡方案继续保留为兼容配置，不能把配置校验等同于设备实测。

完成本题不需要训练大语言模型。表格与短信算法可以用 CPU；GPU 主要用于部署代码 LLM、增加上下文容量和同时处理多个生成/修复任务。当前单卡可完成全部功能目标，六卡主要用于提高本地模型能力、吞吐和消融实验效率。

主架构一开始就拆分成应用、LLM 推理服务、CPU 算法 worker 三部分。卡数通过配置表达，不能在业务代码中写死 cuda:0 或六卡 world size。

## 2. 当前环境的真实检查

本次发现 NVIDIA GeForce RTX 4090 一张，nvidia-smi 显示 24,564 MiB 显存；并未检测到 D 型号，所以当前实测不能标成 RTX 4090D 实测。容器 cgroup 内存上限 16 GiB、CPU quota 相当于 18 核；系统可见的 128 逻辑核和约 252 GiB 宿主内存不是本容器独占额度。

Python 3.10.8；准备脚本使用独立 .venv。当前未发现 Docker 和 uv 命令。本轮没有安装 vLLM、没有下载大模型权重、没有启动多 GPU 服务；GPU 推理耗时和六卡能力尚未实测。

当前 CPU 人工基线最大训练耗时约 1.74 秒、单进程峰值 RSS 约 172 MiB，详见 04 文档。正式 worker 仍按 2 CPU、2 GiB、120 秒留余量。多进程总 RSS、模型进程、容器和 UI 开销需另外测量。

## 3. 资源档位（工程建议，不是实测下限）

| 档位 | CPU | 主机/容器内存 | GPU | 可用磁盘 | 适用 |
|---|---:|---:|---|---:|---|
| API 基础版 | 4 核 | 8 GiB | 无 | 20 GiB | 开发核心闭环，算法单任务 |
| API 推荐版 | 8 核 | 16 GiB | 无 | 50 GiB | UI、知识库、2 个受限算法 worker |
| 当前单卡稳妥档 | 8–16 核 | 16 GiB 可试 7B 量化；推荐 32 GiB | 1×24 GB | 80 GiB | 一个推理服务，短上下文，低并发 |
| 双卡模型档 | 16 核 | 推荐 64 GiB | 2×24 GB | 150 GiB | 32B AWQ TP=2 或两个单卡副本 |
| 四卡模型档 | 16–24 核 | 64–128 GiB | 4×24 GB | 250 GiB | 32B BF16 TP=4，或两个双卡组 |
| 六卡实验档 | 24–32 核以上 | 最低规划 64 GiB，推荐 128 GiB；重并发考虑 192–256 GiB | 6×24 GB | 500 GiB NVMe | 三个双卡组，独立调度多任务 |

16 GiB RAM 加六张卡并不自动成为充裕环境：模型加载、page cache、多个 serving 进程、编译与算法 worker 都消耗 RAM。扩卡同时要调整容器 memory.max、CPU quota、共享内存、磁盘缓存和进程限制。

## 4. 可复现模型基线与显存估算

以官方 Qwen2.5-Coder Instruct 的 7B / 14B / 32B 作为已确认公开可用的兼容基线，优先官方 AWQ 权重。它们是为稳定复現选定的候选，不宣称是当前最先进模型。真正选择前用本项目固定需求集比较输出 schema 成功率、代码可运行率、修复效果和耗时；更强新模型通过 provider 接口替换。

| 候选 | 估算资源与起始设置 | 建议 |
|---|---|---|
| 7B AWQ | 单卡，8K 总上下文，max_num_seqs=2；实际工作集预留约 6–10 GiB 起 | 当前 16 GiB RAM 下的首个本地候选 |
| 14B AWQ | 单卡，8K 总上下文，max_num_seqs=2；工作集约 10–18 GiB 起 | 单卡增强候选；建议主机 32 GiB RAM |
| 32B AWQ | 约 16.25 GB 的理想 4-bit 参数下限，实际含未量化参数/元信息/运行时更高；按双卡规划 | 不承诺单卡 24GB 长上下文稳定运行 |
| 32B BF16 | 约 65 GB 仅权重理论值，再加 KV 与运行时 | 四卡 TP=4 是可试部署档，不用双卡硬装 |

以上工作集区间是容量规划推算，不能当作实测。vLLM 会根据 gpu-memory-utilization 保留更大的 KV 空间，因此 nvidia-smi 中的占用可能接近配置上限。量化格式、kernel、模型 revision 和上下文长度都影响结果。

估算公式：权重字节数约为参数数量 × 每参数字节数；实际显存 = 权重 + 量化元信息/未量化层 + KV cache + 临时激活/算子 workspace + 框架开销。

KV 近似：2 × 层数 × KV heads × head_dim × token 数 × 并发序列数 × KV 每元素字节数。以 32B 配置的 64 层、8 KV heads、head_dim=128、BF16 KV、8,192 token 为例，单序列未分片 KV 约 2 GiB；这是估算，不包括内存分页和其他开销。

max_model_len 是输入与输出总 token 预算，不是仅输入长度。默认给输出保留 2,048 tokens；若代码需更长，先缩小检索证据再调输出预算。不要直接使用模型宣传的 128K 上下文。

## 5. 六卡部署的正确形态

4090D 官方规格为 24 GB GDDR6X、不支持 NVLink。六卡合计标称 144 GB，但并不是一个自动可用的 144 GB 内存池；跨卡模型需要框架切分，受显存分布、PCIe 拓扑、通信后端和模型维度影响。不能承诺六倍速度。

Qwen2.5-Coder-32B 配置有 40 个 query heads，不能直接将其按六等份做常规 TP。默认只采用已匹配架构整除条件的 TP=1/2/4；不是所有模型都通用。多卡 KV 分片和量化 kernel 还需在锁定 vLLM 版本上实测。

### 推荐六卡档：三个双卡组

~~~text
GPU 0,1 → 32B AWQ, TP=2 → endpoint A
GPU 2,3 → 32B AWQ, TP=2 → endpoint B
GPU 4,5 → 32B AWQ, TP=2 → endpoint C
                         ↓
            应用侧统一队列、健康检查、限流与路由
                         ↓
        Planner / Coder / Reviewer 按任务分配，CPU worker 独立
~~~

三个 endpoint 可以承载同一模型的独立副本，增加并发并减少任务排队；不要给每个 Agent 永久独占一张 GPU。正常运行可先只启动一个组，实验时再启用其余组。

### 备选六卡档

- 6×单卡 14B AWQ：模型相同、任务独立时最容易扩大实验吞吐，基本不要求跨卡模型通信。
- 4+1+1：四卡 32B BF16 做主生成；两个单卡 7B/14B 服务做辅助或对照实验。需要先证明更高质量值得额外资源。
- 部分 GPU 故障：摘除整个受影响 TP 组；任务按幂等 ID 重试到健康组。不能在运行中临时把 TP=2 改为 TP=1 继续同一个 worker。
- 如果六张卡分属多台机器，优先每机单卡/双卡服务，经 HTTP 汇聚；不默认跨普通网络做 tensor parallel。

## 6. 配置与调度要求

configs/inference_profiles.json 描述 GPU 分组、model_id、量化、TP、context、序列并发和端口；scripts/plan_inference.py 只校验并打印启动规划，不会下载权重或启动服务。

要保证：同一卡不能被两个 profile 组同时占用；端口不重复；设备数与 TP 匹配；attention heads 能按 TP 划分；容器启动后物理卡 ID 与内部逻辑编号对应正确。生产使用 GPU UUID 更稳定，CUDA_VISIBLE_DEVICES 里的编号只作为本机样例。

应用 provider 只感知 endpoint、served_model_name、模型能力、健康、并发和成本，不感知具体卡。设置 per-endpoint semaphore、总队列上限、请求超时、熔断和带 request_id 的幂等重试。多个 agent 对同一 endpoint 的调用共享预算，防止重试风暴。

单卡流程顺序运行，候选 CPU 任务限制并发；六卡再逐步增至 2/4/6 并行 run。CPU worker 数要由 CPU/RAM 剩余额度决定，不能因为有六张卡就自动开 36 个算法进程。

## 7. 部署前预检

1. 固定模型 revision 和 tokenizer revision；核对模型许可与权重 SHA/缓存；禁止加载来源不明的 remote code。
2. 固定 serving 镜像 digest/依赖，核对 GPU 驱动、PyTorch、CUDA 和量化 kernel 组合。不要照抄一条“安装最新版”指令就视为兼容。
3. nvidia-smi、nvidia-smi topo -m、容器 cgroup、共享内存和磁盘检查。
4. TP 组先做受控通信与小请求预检；记录 P2P/PCIe 情况，不假设 GeForce 一定支持某条直接传输路径。
5. 先 2K context、并发 1，再升到 8K；记录实际显存、RAM、TTFT 与吞吐；OOM 时先降并发/上下文，必要时换更小模型。
6. 再启动第二组/第三组，观察 host RAM、模型加载瞬时峰值与排队。
7. 使用网络鉴权与私网访问推理服务；不要把无鉴权端口直接暴露公网。

生成代码 sandbox 的禁网/低权限与 LLM serving 的 GPU/通信权限应严格分开。不要为了模型并行，把算法 worker 改成 privileged。

## 8. 供电、散热、机箱与存储

官方 4090D 显卡总功耗标称 425 W，六卡 GPU 部分标称合计 2,550 W；整机墙上功耗还包含 CPU、内存、风扇、电源损耗，不能按六卡相加值选一只普通桌面电源。多卡服务器应由设备供应商确认电源冗余、供电回路、散热、显卡间距与 PCIe 通道配置。

磁盘容量按模型缓存、环境、制品和日志分开限额；三个副本可共用只读权重缓存以减少下载，但加载峰值与进程开销仍需测。按 run 清理临时目录，不删除已发布报告和验证证据。

电量预算公式：实测墙上平均功率 kW × 使用小时 = kWh；再乘实际电价。仅用六卡 2.55 kW 乘时间只能得到 GPU 标称部分的参考，不能当整机实测电费。租用成本采用用户实际账单价 × 卡数 × 小时，不在本方案编造当前租赁报价。

## 9. API 与实验预算

即使有本地 GPU，也保留可切换 API provider，便于质量对照和故障恢复。密钥通过环境变量注入，不提交 Git；日志脱敏。

开发预算建议按 100–150 次完整 run 预留；常见单次规划估算为输入 30K–80K、输出 5K–15K tokens。实际因候选、证据长度和修复次数变化，以计数器为准。缓存稳定证据、按错误位置修补、限制候选数可降低调用量。

计算公式：成本 = 未缓存输入 tokens × 未缓存单价 + 缓存输入 tokens × 缓存单价 + 输出 tokens × 输出单价，均除以 1,000,000。
2026-09-28 官方 Flash 美元价快照保存在 configs/api_pricing_snapshot.json：非高峰缓存命中输入/未命中输入/输出为 0.003/0.15/0.6 美元每百万 tokens，高峰为两倍。
来源为 https://api-docs.deepseek.com/quick_start/pricing/ ，后续会变化；估算不等于账单。
银行六候选真实运行使用 83,104 输入（50,176 缓存命中）与 3,493 输出 tokens，按快照约为 $0.0072–$0.0145；没有把 token 数当作实际扣款凭证。

单次上限建议 24 calls、200K input tokens、40K output tokens、900 秒，触及任意一个立即终止并记录。正式 144-run 消融先通过 smoke，再按已测 token 消耗估算总预算；不要无限自我修复。

## 10. 本阶段完成标准

当前已实际完成 API + CPU 算法验证：银行六候选全流程 73.803 秒，短信两候选 18.802 秒（单次观察，不能当作 SLA）。这两组候选单 worker 峰值 RSS 约 188–244 MiB；银行树模型训练约 1.35–3.40 秒，受并发与机器负载影响。完整数据见 examples/evidence/bank_beam/ 与 examples/evidence/sms_transfer/。
单卡到六卡的资源分组、配置检查器和待测清单已准备。新增六卡设备后，依次验证单个 TP 组、三个副本、故障切换、吞吐和内存；只有这些结果实际产生，README 才能把“设计支持六卡”改为“已验证六卡部署”。
