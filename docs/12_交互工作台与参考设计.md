# 交互工作台与参考设计

## 参考范围与独立实现

工作台围绕“先读结论、再看证据、最后回到知识”的研发阅读路径设计。界面组件、页面样式和数据适配均由本项目独立实现，并以算法能力复刻任务的固定数据协议、验证证据和知识回写为中心。

| 交互原则 | 本项目的实现 |
| --- | --- |
| 图谱探索优先呈现关系上下文 | D3 画布支持拖拽、缩放、节点选择、关系筛选和一跳/两跳邻域探索 |
| 证据沿来源和运行路径展开 | 侧栏展示来源定位、内容哈希、能力版本、验证运行和制品关系 |
| 报告先给结论，再展开过程 | 候选比较、检查状态和主指标位于首屏；计划、修复、代码和原始 JSON 使用折叠区 |
| 交互结果保持事实可追溯 | 前端只消费 FastAPI 返回的结构化事实，不读取 API Key、SQLite 文件或执行生成代码 |

页面使用固定的领域词汇、状态颜色和图标语义，避免把中间态误认为最终结论。运行事件、指标和制品哈希均来自后端报告，界面不生成虚构进度。

## 页面与技术选择

工作台采用 Vue 3、TypeScript、Vue Router、Vite、D3 与 `@lucide/vue`。Vue 管理表单、报告和路由状态；D3 提供关系布局及画布交互；Lucide 图标使用统一样式并配合文字标签。FastAPI 继续负责执行、保存和提供事实数据，浏览器不直接读取 SQLite、API 密钥或执行生成代码。

| 页面 | Hash 路由 | 主要交互 |
| --- | --- | --- |
| 工作台概览 | `/app/#/` | 查看近期运行、能力与关系统计，选择行业示例 |
| 创建算法任务 | `/app/#/workbench` | 输入需求、选择数据/后端、高级预算、复用历史或能力 |
| 运行与验证报告 | `/app/#/runs/{run_id}` | 跟踪事件、取消运行、比较候选、展开证据、下载交付物 |
| 知识探索 | `/app/#/knowledge` | 图谱与能力库切换、筛选、选中、聚焦、溯源、版本查看 |
| 运行历史 | `/app/#/history` | 最近 50 次记录，搜索和按场景/模式/状态筛选 |
| 模型与环境 | `/app/#/settings` | 查看后端配置、本地推理计划和执行边界 |

报告、图谱和历史互相连接：报告可跳到关联能力或验证运行节点；能力详情可将能力摘要带入新需求；历史需求可复用为新运行。原始记录继续保留，新的提交创建新的运行 ID。

## 构建与启动

需要 Python 项目虚拟环境、Node.js 22.12+ 和 npm。Python 安装、数据校验与知识初始化步骤见 [README](../README.md)。在仓库根目录执行：

~~~bash
./scripts/build_web.sh
./scripts/start_api.sh
~~~

另开一个终端运行：

~~~bash
./scripts/start_ui.sh
~~~

- `build_web.sh` 在 `web/` 执行 `npm ci` 和 `npm run build`，依据锁文件安装依赖并完成类型检查及构建。
- `start_api.sh` 默认在 `127.0.0.1:8000` 启动 API，同时挂载 `/app/` 静态工作台。
- `start_ui.sh` 默认在 `127.0.0.1:8501` 启动同源网关，将页面 API 请求转发到 `ALGOFORGE_API_URL`，默认值为 `http://127.0.0.1:8000`。网关不创建第二个工作流执行器。
- 两个端口都可以访问工作台；8501 用于保留熟悉的 UI 入口，8000 可以直接提供页面和 API。根路径会跳到 `/app/`。
- `node_modules/` 与 `dist/` 不提交到 Git。首次克隆要构建；前端源码变化后需重新构建。如果服务启动时没有构建目录，会显示构建提示，构建后重启对应服务。
- `start_ui.sh` 发现构建缺失时会尝试调用构建脚本；此行为不自动安装 Node.js。构建脚本兼容当前机器已有的用户目录 npm 入口，但新机器仍需要自行提供可用的 Node/npm。
- 可选旧界面使用 `./scripts/start_legacy_ui.sh`。它需要 Streamlit 依赖，默认也占用 8501；与新版同时运行时应设置不同 `ALGOFORGE_UI_PORT`。

Hash 路由支持页面刷新，开发前端可以在 `web/` 运行 `npm run dev`；后端需要同步启动，代理配置见 [vite.config.ts](../web/vite.config.ts)。应用容器使用 Node 构建阶段加 Python 运行阶段，详情见 [部署说明](../deploy/README.md)；Docker 部署结果以目标环境验证记录为准。

## 图谱接口与真实证据

典型请求如下，节点 ID 放在查询参数中，支持包含冒号的真实 ID：

~~~text
GET /graph/explore?focus=capability:某能力ID:v1&hops=2&limit=80&edge_limit=160
GET /graph/explore?kinds=Capability,Algorithm&relations=USES,DERIVED_FROM&q=logistic
GET /capabilities/某能力ID?version=1
~~~

`nodes` 提供 ID、类型、名称、属性、中文类型名和到中心的距离；`edges` 提供真实源、目标、关系与属性。`facets` 是全局图例和数量，`stats` 明确总量、匹配量、返回量及遗漏量，`truncated` 表示是否因上限截断。选择节点可查看来源、运行、制品或失败经验；能力详情另外提供卡片全文和版本记录。

证据沿持久化来源关系连接，展示来源 URI、定位、内容哈希及验证路径。能力验证依据完整运行路径和验证结果判断；共享数据集需要结合具体特征策略与指标证据。图谱检索采用词项匹配与图扩展，向量检索和训练后的知识表示列入后续扩展。完整解释见 [前端与报告说明](11_前端与报告说明.md)。

## 可执行的交互验收

1. 完成构建与 API/UI 启动，访问 `http://127.0.0.1:8501/app/`。首页加载真实本机历史，空数据库显示引导，服务失败显示明确错误状态。
2. 进入“创建算法任务”，选择银行或短信示例，使用 Mock 提交。确认跳转到新的运行 ID，运行事件和候选状态随后端更新。Mock 不产生模型调用费用，也不计作真实 LLM 效果。
3. 在报告中检查主指标、基线和候选分母，切换候选后查看对应逐项检查。展开修复、来源、代码和事件，确认初始状态下完整 JSON 不铺开；下载 JSON、Markdown、代码并打开 HTML 报告。
4. 检查失败、取消、无指标或缺少检查的记录，确认未记录值没有被填零，`baseline_or_worse` 不显示为质量通过。若需要稳定复现这些界面状态，使用下述浏览器测试夹具。
5. 从报告跳到知识图谱，点击节点查看右侧证据，切换一跳/两跳，筛选节点与关系，拖拽和缩放画布。留意当前显示数量与全局数量的区别，清空筛选后恢复概览。
6. 打开能力库，查看来源与版本，点击“用于新任务”检查带入的能力摘要；在运行历史中复用需求，确认创建新任务而非覆盖原运行。
7. 模型与环境页检查当前配置。本地模式仍明确标注接入待验证；仅有配置不能作为 GPU 部署、连通性或吞吐证明。

前端自动化命令：

~~~bash
./scripts/build_web.sh
cd web
npx playwright install chromium
npm run test:e2e
~~~

[frontend.yml](../.github/workflows/frontend.yml) 在 GitHub Actions 中执行锁文件安装、类型检查/构建及 Chromium 交互检查，并保存 Playwright 报告。测试使用拦截的 HTTP 夹具，不需要任何模型密钥；它证明交互按给定响应工作，不能替代真实后端闭环、LLM 调用、本地 GPU 或 Docker 部署验收。最终测试数量与实测记录由主验证索引单独记录。
