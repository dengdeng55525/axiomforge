# 使用与演示指南

本指南对应 API 驱动的原型：当前使用 DeepSeek V4.1 Flash API（实际 ID：deepseek-flash）完成语言理解、规划、生成与修复；银行营销响应预测为主场景，短信垃圾信息分类用于检验同一框架的迁移。名称与 ID 对应关系保存在 [模型发现记录](research/deepseek_model_discovery.json)。本地 14B OpenAI 兼容 Provider 和四卡静态 profile 已接好，但本轮不下载权重、不启动本地大模型，也不把 1–6 张 4090D 配置写成已完成的多卡性能实验。

旧方案文档中的 Docker、完整 144 次消融等是路线规划。当前实现能力应以代码、doctor 输出、运行报告及实际测试结果为准。

## 1. 启动前检查

在项目根目录工作。首次在新机器创建环境时运行：

~~~bash
cd algorithm-capability-factory
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install -e '.[dev,ui]'
python scripts/verify_data.py
python -m capability_factory --help
python -m capability_factory doctor
~~~

algoforge 和 python -m capability_factory 是同一 CLI 的两种入口。已有 .venv 时直接激活即可；不要覆盖已经配置的未提交 `.env`。

需要确认：

- 使用 Python 3.10 及以上，实际版本与依赖以安装结果和 doctor 输出为准。
- data/raw/bank-additional-full.csv 与 data/raw/SMSSpamCollection 存在，数据审计哈希匹配。
- API 服务进程能读取数据目录并写入 artifacts 输出目录。
- 凭证只配置在后端环境，不能填入页面需求、日志、截图或 Git 文件。
- 当前走云端 API，本地 GPU 不是运行原型的前提；算法训练与评估仍占用 CPU 和内存。
- 预留本地路线默认是 `four_gpu_14b`：Qwen2.5-Coder-14B-Instruct-AWQ 的四个单卡副本，端口 8100–8103；完整规划见部署说明。

云端模型配置由后端读取，不在 UI 中编辑：

| 变量 | 作用 | 本项目默认 / 约定 |
|---|---|---|
| DEEPSEEK_API_KEY | API 凭证 | 未提交的环境变量或 `.env` |
| DEEPSEEK_BASE_URL | 模型 API 地址 | https://api.deepseek.com |
| DEEPSEEK_MODEL | 实际调用的模型 ID | deepseek-flash，以服务响应与运行记录为准 |
| ALGOFORGE_ROOT | 项目根目录 | 默认从安装目录确定 |
| ALGOFORGE_API_URL | UI 连接的业务 API | http://127.0.0.1:8000 |

产品名称与可调用模型 ID 可能不同。答辩中应展示实际请求/响应中的 model，不把口头名称当作已验证的 API 模型 ID。

~~~bash
python -m capability_factory doctor --check-api
~~~

此操作连接模型服务。模型列表可访问不等于生成请求已经成功；真实调用证据来自完整 run。

## 2. 完成第一条闭环

### 初始化知识库

先用无付费模型调用的方式检查准备流程：

~~~bash
python -m capability_factory init --provider mock
~~~

需要真实模型抽取示例时使用：

~~~bash
python -m capability_factory init --provider deepseek
~~~

报告与知识来源必须保留实际 mode。init --provider mock 导入有来源的人工种子，不调用 LLM；它可验证解析、持久化与图结构，但不能充当真实模型完成能力抽取的证据。真实抽取已有 9 张来源检查通过的卡，公开结果见 [knowledge_extraction.json](../examples/evidence/knowledge_extraction.json)；来源检查通过不等于这些卡对应的算法全部通过运行验证。

### 银行主场景

~~~bash
python -m capability_factory run \
  --description '预测银行客户是否订购定期存款，只使用通话前特征，禁止 duration。比较两个方案，以验证集 AP 选择候选，报告接口、稳定性、修复和资源。' \
  --dataset bank \
  --provider deepseek \
  --max-candidates 2 \
  --max-repairs 2 \
  --search compare \
  --use-graph \
  --max-seconds 900
~~~

预期得到 run_id、状态、候选、验证指标、来源与制品路径。实际结果可能通过、失败、超预算或取消；失败报告同样保存，不要手工改成通过。银行任务是定期存款营销响应，不是客户流失。

需求与固定数据协议冲突时应展示拒绝或约束说明，不能恢复泄漏特征来抬高指标。

### 跨场景短信任务

~~~bash
python -m capability_factory run \
  --description '构建短信垃圾信息分类能力，比较 TF-IDF 线性分类与朴素贝叶斯，输出概率接口、AP、F1、检查和来源。' \
  --dataset sms \
  --provider deepseek \
  --max-candidates 2 \
  --max-repairs 2
~~~

这里复用同一编排、候选验证、报告与知识回写机制。文本特征处理由任务插件与受限构造接口确定。迁移演示应解释变化的是数据契约、预处理与指标配置，不能声称任意未知行业都已验证。

### 搜索与有限修复

~~~bash
python -m capability_factory run \
  --description '构建银行营销响应预测，依据历史失败经验与验证 AP 搜索合法方案。' \
  --dataset bank \
  --provider deepseek \
  --search beam \
  --max-candidates 6 \
  --max-repairs 2 \
  --use-graph
~~~

6 是候选上限，不是承诺一定评估六个合法不同方案。查看候选 parent、变化内容、验证分数、剪枝理由与预算，确认不是把多个相同请求简单命名为 Beam Search。

修复演示可加入 --inject-failure，产生明确标记的注入故障，观察错误分类、修复前后制品哈希与检查变化。**注入错误修复率必须与真实生成错误修复率分开统计。**

--provider mock 可低成本检查闭环，但仍可能有 CPU 训练开销。Mock 指语言模型响应模拟，不能把这种运行展示成真实 API 生成。

## 3. 启动 API 与 Vue 工作台

第一个终端启动业务 API：

~~~bash
cd algorithm-capability-factory
source .venv/bin/activate
python -m capability_factory serve --host 127.0.0.1 --port 8000
~~~

第二个终端构建并启动 Vue 工作台网关：

~~~bash
./scripts/build_web.sh
./scripts/start_ui.sh
~~~

打开本机 `http://127.0.0.1:8501/app/`；API 也直接提供 `http://127.0.0.1:8000/app/`。界面只通过 HTTP 调用业务 API，不导入评估器、不执行生成代码、不读取模型凭证。UI 网关只转发白名单 API 路由。

工作台包含概览、任务、报告、知识探索、历史和环境六个页面；缺失指标显示为未记录，不转成零。旧版 Streamlit 如需兼容可运行 `./scripts/start_legacy_ui.sh`，但不是默认入口。

| 页面 | 操作与证据 | 不应误读的地方 |
|---|---|---|
| 任务与监控 | 需求、任务类型、真实/模拟模式、候选数、步骤与取消 | 刷新只是读取状态，不触发新模型调用 |
| 代码与报告 | 候选指标、检查、修复链、哈希、只读代码和下载 | 下载代码不等于允许在宿主机任意执行 |
| 知识图谱 | 能力版本、节点/关系、来源、验证记录和导出 | 布局最多画 120 个节点；完整记录保留在表中 |
| 历史与资源 | 模式筛选、历史运行、最多四次运行的资源表 | 跨任务 AP 不直接排名；CPU 耗时不等于云端 GPU 耗时 |

监控默认手动刷新，可开启每 3 秒刷新。左侧可输入已保存的运行 ID。读取历史真实 API 记录不会重跑请求；mode 表示记录产生方式，不能把查看历史记录称为当前实时执行。只有系统明确生成 mode=replay 才标记回放模式，当前没有独立的回放执行入口。

API 断开显示连接错误；没有指标时保留空值或“未记录”。界面不补零、不伪造成功、不静默切换 mock。

## 4. HTTP 接口示例

提交一个明确标记为模拟的工程检查任务：

~~~bash
curl --noproxy '*' -sS http://127.0.0.1:8000/runs \
  -H 'Content-Type: application/json' \
  -d '{"description":"构建银行营销响应预测，禁止 duration，比较两个候选。","dataset_id":"bank","provider":"mock","max_candidates":2,"max_repairs":2,"use_graph":true,"search":"compare","inject_failure":false}'
~~~

响应包含 run_id 与 status。将下表的 {run_id} 替换为实际响应，制品 ID 同理。示意 ID 不是验收结果。

| 方法与路径 | 用途 |
|---|---|
| GET /health | 服务、模型、执行后端和本地模型部署状态 |
| GET /config | Provider、数据集、上限和安全边界（无密钥） |
| GET /inference/profiles | 四卡 14B 静态推理计划 |
| GET /runs/{id}/timeline、/metrics、/resources、/summary | 可视化专用时间线、指标、资源和汇总 |
| POST /runs | 提交受限任务对象 |
| GET /runs | 历史运行列表 |
| GET /runs/{run_id} | 状态与事实 |
| GET /runs/{run_id}/events | 可追溯步骤，非隐藏思维链 |
| GET /runs/{run_id}/artifacts | 制品元信息 |
| GET /runs/{run_id}/artifacts/{artifact_id} | 代码与哈希 |
| GET /runs/{run_id}/report | 原始 JSON 报告 |
| GET /runs/{run_id}/report.html | 独立 HTML 报告 |
| POST /runs/{run_id}/cancel | 申请取消，以后端终态与回收记录为准 |
| GET /capabilities | 能力与版本列表 |
| GET /graph | 节点及有向边 |

提交对象使用 description、dataset_id 与 provider。UI 支持 bank/sms 和 deepseek/mock，不提供任意文件路径、模型地址或 shell 命令输入。高级接口约束与可选项以 OpenAPI schema 为准。

## 5. 报告导出与取证

用实际运行 ID 替换 RUN_ID：

~~~bash
python -m capability_factory report RUN_ID --format html --output artifacts/demo-report.html
python -m capability_factory report RUN_ID --format json --output artifacts/demo-report.json
python -m capability_factory report RUN_ID --format markdown --output artifacts/demo-report.md
python -m capability_factory export-graph --output artifacts/graph.json
~~~

HTML 报告包含运行身份与模式、原始需求与约束、数据与证据、候选指标与检查、资源与修复链、制品哈希、调用用量与计时、知识回写、警告、事件和原始报告。

报告层只渲染传入事实，不自行增加成功状态、AP、参考分数或基线。null、非有限数值和缺失记录不转成零；JSON 保留事实结构，HTML 明确显示未记录。动态文本经过 HTML 转义，HTML 没有外部脚本、CDN 或字体依赖。UI 下载该报告，不直接嵌入任意后端 HTML 执行。

验收时同时保留 JSON 与 HTML：前者用于机械复核与汇总，后者方便阅读。制品哈希绑定具体版本，修改同名文件后不能沿用旧哈希宣称新版本已验证。

## 6. 读懂状态、指标和成本

status 描述工作流，quality_status 描述质量门槛，两者应分别查看。接口正确但泛化不足仍要披露，代码构造成功也不等于所有稳定性、资源与安全检查通过。

- AP 使用 average_precision_score，不能与另一种 PR 曲线面积计算混称。
- 选择候选只使用验证集，最终测试不能反馈给搜索或修复。
- 银行仅使用通话前特征，不能恢复 duration 抬高成绩。
- 短信的重复文本与切分按数据契约处理，不能泄漏最终测试。
- 常数、人工参考与 Agent 候选须使用同一协议，并标明产生方式。
- 失败候选的空指标不是零，也不是静默删除失败样本的理由。
- 阈值 F1、名单提升率与 AP 衡量不同目标，不能相互替代。

算法 fit 时间、worker 峰值 RSS、端到端时间、模型请求延迟和 token 用量分列。单次调用不能推出 p95；没有计费依据时不编造人民币费用。真实、mock 与 replay 分开统计，失败与取消运行保留在分母中。

## 7. 当前执行范围与后续兼容

执行后端为 constrained_ast_subprocess：严格检查生成的 build_pipeline AST，使用白名单构造解释器，只允许受支持的 sklearn 管道/估计器构造；不以 Python exec/eval 执行模型文本。可信执行器构造对象并训练，独立进程施加资源、时间及环境限制，模型凭证不应传给算法 worker。

**这不等于 Docker、虚机或操作系统级不受信代码隔离。** 原型面向固定数据和受控算法构造，不能宣传为能安全执行任意上传代码的公网服务。旧设计中的容器隔离是后续增强项，答辩应说明当前边界和限制执行语言的设计选择。

本地模型预留 provider/endpoint 边界；1 卡与最多 6 张 4090D 规划见 [算力预算与六卡兼容](05_算力预算与六卡兼容.md)。当前功能验证不依赖多卡到位。切换本地端点后，仍需重新验证接口、模型 ID、上下文、结构化输出、生成质量、并发、OOM、回收与吞吐，不能套用云端 API 的延迟结论。

## 8. 建议 8–10 分钟演示

| 时间 | 操作 | 证据 |
|---|---|---|
| 0–1 分钟 | 说明银行营销任务和公开数据 | 业务目标、来源、禁用 duration、固定切分 |
| 1–3 分钟 | 提交真实 API 任务 | 实际 model、约束、检索来源与角色事件 |
| 3–5 分钟 | 展开候选与报告 | 两套代码、哈希、统一检查和指标/资源比较 |
| 5–6 分钟 | 展示修复与回写 | 原错误、补丁、检查变化及经验适用范围 |
| 6–7 分钟 | 展示短信任务与图谱 | 同一流程处理文本，能力版本与来源路径 |
| 7–9 分钟 | 展示测试与实验 | 失败分母、模式分离、图检索和搜索的实际效果 |
| 最后 1 分钟 | 展示复现、Git 和限制 | 命令、依赖、运行 ID、执行边界和多卡待测 |

至少准备一条真实 API 闭环和一条独立标记的故障注入修复示例。网络不稳定时打开已保存报告，说明这是历史实测；不要把保存的事件打印成实时调用。模式标签不能替代来源证据。

现场不要求跑完 144 次实验。完整矩阵需独立执行并汇总，未执行的格子写未执行；小样本描述性结果不能宣称统计显著。

## 9. 测试与自检

~~~bash
python -m pytest tests ui -q
python -m pytest tests/test_reporting.py ui/test_ui.py -q
python -m ruff check src tests ui
~~~

tests/test_reporting.py 覆盖动态文本和指标名转义、模式标记、空结构、不伪造指标、固定导出路径、非有限数处理及 Markdown 围栏。ui/test_ui.py 使用 Streamlit AppTest 与模拟 HTTP 契约覆盖四视图、提交参数、模式选择和断线提示，不访问付费模型，也不代表真实后端 E2E 已通过。

后端、数据集实跑与真实 API 示例须独立核验。未装 UI 可选依赖时 UI 测试可能跳过，跳过不能写为已验证。

## 10. 常见问题

| 问题 | 处理 |
|---|---|
| 页面无法连接 API | 启动 serve，检查 ALGOFORGE_API_URL、端口及 /health |
| 凭证或模型 ID 错误 | 后端检查配置与 doctor --check-api；不截图泄露凭证 |
| 生成结构不合法 | 查 schema 错误、事件与重试预算；上限耗尽应失败 |
| 候选没有指标 | 查静态拒绝、超时或预测检查；保留缺失，不补零 |
| 所有候选 AP 偏低 | 对照同协议基线、特征与时间分布；不反复改测试协议挑分 |
| 没有代码制品 | 查生成阶段、events 与 artifacts，不把页面空白解释为通过 |
| 图谱很小 | 展示实际影响约束或修复的路径，不添无证据节点 |
| 取消后暂未终止 | 查服务端状态、请求超时和 worker 回收，按钮不是终止证明 |
| 单卡或没有 GPU | 当前 API 路线仍可继续，本地和多卡实测属于下一阶段 |

高分来自可复核闭环、模块边界、真实数据和诚实实验。最终提交按 [开发清单与验收矩阵](06_开发清单与验收矩阵.md)，逐项绑定代码入口、测试、真实运行 ID 与报告路径。

## 11. 批量实验与证据清单

先检查计划，不调用模型：

~~~bash
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 --dry-run
~~~

再运行无模型计费的工程 smoke：

~~~bash
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 \
  --profiles A,B,C,D --case-ids B01,S01 --output artifacts/experiments/mock-smoke
~~~

需要真实模型对照时显式改成 --provider deepseek；先检查 dry-run 和预算，再决定运行规模。常规 smoke 每轮 8 次，full 每轮 48 次，full 三轮共 144 次；任务/配置筛选后数量随计划改变。Mock 仍会训练 CPU 算法，不能把它当作零资源开销。

| 配置 | 检索 | 编排 | 候选/修复上限 |
|---|---|---|---|
| A | 无检索 | single_shot | 1 / 0 |
| B | 文本检索，无图加分 | single_shot | 1 / 0 |
| C | 文本与图检索 | single_shot，带修复路径 | 1 / 2 |
| D | 文本与图检索 | multi_role + beam | 6 / 2 |

准确配置以 scripts/run_experiments.py 和生成的 plan.json 为准。CLI 同时提供 --use-retrieval/--no-use-retrieval 和 --orchestration single_shot/multi_role；A 的无检索由 use_retrieval=False 实现，不能只用 --no-use-graph 冒充。默认业务运行是 multi_role，UI 保留简单的默认设置，完整对照由实验脚本控制。

每个 job 使用独立知识库，避免较早运行的回写污染较晚组；因此这套实验不能用于证明跨运行经验学习效果。任务共享数据切分、结果相关；C/B 与 D/C 同时改变部分机制，不是每一组都能作单因素因果解释。

检查计划、原始记录、汇总和限制说明。失败/取消保留在分母中，未开始任务不是实际观测。没有完整实验结果前，不填写成功率提升、统计显著性或 API 总费用结论。

首次真实银行修复示例 ID 为 13edb7649f0d41bba608251b6079e4d1：两个候选中一个通过、一个失败，API 调用 11 次，首个候选包含标记的故障注入并自动修复。历史记录证明这一次运行，不替代最新代码回归。最终测试数量、样例状态、哈希与路径统一查 docs/research/execution_validation.json。
