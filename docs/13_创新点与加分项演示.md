## 1. 固定版本的仓库能力抽取

ingest-repo 面向本地 Git 仓库。操作者选择 Python 文件、来源地址、许可证和适用任务；系统直接读取指定提交中的 Git blob，以静态 AST 解析抽取能力，来源固定到提交快照。

以下用本项目的真实指标模块演示，可替换为另一个已审核的本地仓库及其 GitHub 来源地址：

~~~bash
python -m capability_factory ingest-repo . \
  --revision HEAD \
  --path src/capability_factory/metrics.py \
  --repository-url https://github.com/dengdeng55525/axiomforge \
  --license MIT \
  --task-type tabular_binary_classification \
  --task-type text_binary_classification \
  --output artifacts/ingestion/repository.json
~~~

输出包括固定 commit、文件 blob ID 与 SHA256、符号行号、签名、返回注解、docstring、导入语句、能力卡和解析问题。manifest 的内容进入 SQLite，形成 Source → Capability 的来源关系和 Environment 依赖关系，可在知识探索中搜索函数名。

- 支持顶层函数、异步函数、类和类方法，提取静态结构、签名与说明。
- 导入语句记录源码依赖；部署环境使用项目依赖锁文件确定包版本。
- 任务适用性、来源 URL 和许可证由操作者确认并随 manifest 保存，便于来源审核。
- 每次最多 50 个显式 Python 文件、单文件 256 KiB、总计 2 MiB、200 个符号；拒绝路径穿越和符号链接。
- AST 解析问题进入 issues，成功抽取的符号与文件逐一对应。
- Git 命令设置超时，并禁用 hooks、替换对象和懒加载下载；解析过程保持源码静态读取。

**版本演示**：对相同 commit 重复导入，new_capability_versions 为 0；在原仓库提交修改后再次导入，稳定能力 ID 对应新的版本和 SUPERSEDES 边，旧来源与旧版本仍可查看。抽取结果采用 extracted 状态；验证运行另行保存生成算法的执行结果，并与引用能力建立关联。

公开样例：[repository.json](../examples/evidence/innovation/repository.json)。该样例固定到本项目 metrics.py 的真实 Git 提交，保留函数签名、源文件行号与内容哈希，可按相同命令复核。

## 2. 有界多角色搜索与可复用失败经验

~~~bash
python -m capability_factory run \
  --provider local_http --dataset bank --search beam \
  --max-candidates 6 --max-repairs 2 --max-seconds 900 \
  --description '预测银行定期存款订购，仅使用通话前特征，禁止 duration。比较候选并搜索参数变体，输出验证、设计依据、资源与失败修复记录。'
~~~

provider 可选 local_http、deepseek 或 mock，分别用于本地模型、API 和确定性工程验证。多角色由同一个所选后端模型串行承担，每个角色具有独立的上下文与输出合约，运行记录保留各次调用及交接产物。

解释器 → 证据检索 → Planner → Coder → 独立验证器 → Reviewer / Repair Coder → 再验证 → Curator → 版本化知识回写。

检查同一运行的以下证据：

| 设计机制 | 观察位置 | 应看到的事实 |
| --- | --- | --- |
| 证据约束规划 | candidate.plan.evidence_ids | 仅引用本次实际检索到的能力 |
| 有界扩展 | BEAM_EXPANDED、search_tree | 最多两个存活父节点，每个最多两个子节点，全局算法变体不重复 |
| 合约纠正 | RESPONSE_SCHEMA_REJECTED、PLAN_REJECTED | 分别记录格式和语义校验结果，合约通过后进入执行 |
| 真实修复 | attempts、repairs、before_hash / after_hash | 修复后的不同代码重新执行同一验证器 |
| 经验沉淀 | knowledge_writeback.experiences | validated 对应成功修复证据，来源指向运行 |
| 后续可检索 | KnowledgeStore.search | 已验证经验可作为新任务的检索证据，保留任务范围与来源 |

本地模型的一次真实运行中，生成代码出现重复构造错误。Reviewer 给出诊断，Repair Coder 修改代码，同一验证器重新检查后通过，系统形成 1 条已验证经验，完整记录见 [预算、Beam 与修复证据](research/budget_beam_validation.json)。该案例展示自然错误的发现、修复、再验证和经验回写；协作收益与跨任务复用效果可通过 run_experiments.py 的消融配置和重复实验进一步评估。

## 3. 质量与资源的 Pareto 分析

新运行把分析保存到 report.optimization。Web 报告新增“质量与资源权衡”，旧运行也可在 API 读取时获得带 analysis_version 的派生视图，原始存储记录不会因此被重写。

只分析已有报告，不产生 LLM 调用：

~~~bash
python -m capability_factory analyze-run RUN_ID \
  --output artifacts/resource-tradeoffs.json
~~~

**三个目标**：验证 AP 越高越好，训练耗时和 worker 峰值 RSS 越低越好。通过验证且三个测量值齐全、合法的候选进入计算；失败、缺失或非有限值进入 excluded，并保留具体排除原因。

一个候选在三个目标上均不差于另一个、并至少一项更好，才支配后者；不被任何候选支配的集合构成 Pareto 前沿。相同数值的候选不互相支配。父子节点额外输出 AP、训练时间和 RSS 的变化，便于解释搜索变体实际带来了什么。

候选选择遵循预注册的 AP 优先规则，资源分析提供辅助决策视图。当前报告记录每个候选的一次资源观测；RSS 的测量范围为算法 worker 进程。稳定加速、p95 延迟、LLM 显存和跨机器性能由专项重复基准分别测量。

公开实测分析：[resource_tradeoffs.json](../examples/evidence/innovation/resource_tradeoffs.json)。其 run_id 指向已有真实本地模型报告，并明确是历史报告的派生分析。

[本地 14B 短信运行](../examples/evidence/sms_local_resources/report.json)直接在工作流中保存分析结果：两个候选均通过，选中 ComplementNB 的验证 AP 为 0.9598。公开目录同时包含每个候选的实际生成代码、验证记录、哈希清单和可读 HTML 报告；它与银行运行共同展示表格/文本场景复用同一编排。

## 4. 自动生成接口文档

~~~bash
python -m capability_factory export-openapi --output artifacts/openapi.json
~~~

导出内容来自实际 FastAPI 路由和 Pydantic schema；不读取模型凭证、不访问 LLM、不修改运行数据库。可交付给接口测试或客户端生成工具。启动 API 后也可使用 /docs 与 /openapi.json。

公开接口样例：[openapi.json](../examples/evidence/innovation/openapi.json)。部署文件见 [部署说明](../deploy/README.md)，四卡本地模型配置见 [inference_profiles.json](../configs/inference_profiles.json)。接口合约、模型服务和容器运行环境分别按对应指南验收。
