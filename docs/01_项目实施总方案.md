# AlgoForge：基于可验证知识与多角色 Agent 的算法能力工厂

> 文档状态：**设计历史/实施路线**。它记录早期决策和优先级；当前实现以 [README](../README.md)、[实现与验收对照](08_实现与验收对照.md) 和验证索引为准。

方案日期：2026-09-28。依据：docs/source/exam.txt。

## 1. 决策摘要

主选题：银行营销响应预测算法能力工厂。输入一段中文需求，系统抽取约束、检索能力知识、提出多个算法方案、生成代码、隔离运行、自动评估、有限次数修复，并将有证据的能力版本与失败经验入库。第二场景：短信垃圾信息分类，用同一套工作流证明跨场景复用。

此项目交付一个能够验证自身生成算法的系统，包含预测实现、完整闭环和可复现实验。模型 AUC 属于验证证据的一部分。评分中的技术能力与代码质量合计 70%，优先保障真实闭环、清晰接口、可复现测试、失败处理，再投入搜索策略与界面。

建议一位熟悉 Python 的开发者按 12 个工作日、约 84 小时开发，再留 20% 缓冲。若只剩 3–5 天，执行 P0；7–9 天完成 P0 与优先 P1；12–15 天补齐完整实验和迁移演示。以上为规划工时，实际效率以项目记录为准。

硬件兼容目标已经更新为四张 RTX 4090D：单卡可做全流程，四卡用于本地 14B 多副本或 32B TP=4 实验。算法训练默认 CPU；GPU 主要承载 LLM 推理与多个实验的并行。

最终评分取决于评审结果。方案围绕题面每个评分维度安排可检查的实现、测试和展示证据；所有结果遵循真实运行、标签隔离和可复核证据要求。

## 2. 为什么选择这两个场景

| 候选 | 数据与算力 | 主要风险 | 决策 |
|---|---|---|---|
| 银行营销响应 | UCI 官方公开数据，表格模型可以用 CPU | 通话时长泄漏、时序漂移、正类少 | 主场景，可展示业务理解与验证深度 |
| 短信分类 | UCI 官方公开文本，小规模 CPU 即可 | 文本重复造成跨集合泄漏 | 迁移场景，复用引擎，仅替换任务插件 |
| 常见 Telco 流失镜像 | 下载方便，但镜像、字段定义和许可常不一致 | 很容易把另一种预测任务误称客户流失 | 本轮不选 |
| 图像缺陷检测 | 需要图像处理、视觉模型和更大制品 | 开发时间被训练、数据下载和部署消耗 | 不作为主任务 |
| 推荐/库存预测 | 有公开数据，但分组、时间、负采样更复杂 | 容易把验证协议做错 | 后续插件扩展 |

主数据用于预测是否订购定期存款，项目名称统一使用“营销响应/订购倾向预测”。数据集来源、版本、许可和实测统计见 02 文档。

## 3. 最终必须让评委看到什么

一次演示至少产生以下文件与页面：

1. 原始自然语言需求与结构化 TaskSpec，显示输入列、目标、数据划分、业务约束和资源预算。
2. 检索证据列表与关系图，能点到文档来源、真实代码位置和历史失败记录。
3. 2–3 个候选方案及选择依据；展示实际执行结果和 LLM 提供的方案说明。
4. 生成的 model.py、模型接口说明、依赖锁定信息、源码哈希。
5. 验证器产生的 JSON 和 HTML 报告，包括接口、指标、稳定性、资源与安全状态。
6. 至少一次真实失败到修复的证据：错误摘要、补丁、前后测试结果和修复次数。
7. 知识库中的新版本、运行记录和失败经验，第二次相关任务会检索到它。
8. 用相同引擎执行短信分类的迁移演示。
9. 全新环境的一键复现实录、测试结果、清晰 Git 历史与 GitHub README。

示例输入：

> 帮我构建银行营销响应预测算法，用通话前可取得的客户信息预测是否订购。禁止使用通话时长，处理未知类别，输出订购概率与优先联系名单。比较至少两个方案，在 2 核 CPU、2GiB 内存、单候选 120 秒预算内运行，以 AP 和前 10% 联系名单效果评估。

需求中缺失的高影响条件记录为显式假设；自然语言要求超出可用字段时返回可解释的字段边界。

## 4. 范围与投入优先级

### P0：必须交付，先做通

- 一个真实公开表格数据集，以及脚本化下载与校验。
- 文档和代码元信息抽取、结构化能力记录、SQLite 持久化、关系检索。
- 一个真实 LLM 接入；支持明确标识的 mock，供离线测试和故障演示。
- 需求理解 → 检索 → 规划 → 代码生成 → 测试 → 修复 → 回写的闭环。
- 至少两种候选算法、最多两次修复、统一模型接口、统一独立评估器。
- CLI、可复制命令、基础报告、版本与日志、隔离执行。
- pytest、lint、依赖锁定、样例输入输出与证据目录。

### P1：主要高分差异，闭环稳定后完成

- 有限预算 Beam Search，保存搜索树、剪枝理由和各节点评估。
- Planner、Coder、Reviewer、Memory Curator 分角色协作、结构化交接与互相纠错。
- 带适用范围的失败经验检索，避免同类错误反复发生。
- 能力版本、来源追溯、知识关系图、候选比较页面。
- FastAPI + Streamlit：一个后端业务入口，页面和 CLI 都复用它的服务层。
- 真实代码仓库 AST 抽取与出处哈希。
- 单卡/双卡/四卡推理配置及运行健康检查。
- 完整消融实验、资源成本表与可核验演示录像。

### P2：时间充分再做，不作为核心验收依赖

- 短信分类插件及小型跨场景实验，优先于大型部署平台。
- 同机多副本推理调度、不同模型质量/成本路由。
- 可选的向量检索、概率校准、漂移诊断、组间误差分析。
- 未来再考虑微调、MCTS、Kubernetes、Neo4j 集群和多机模型并行。

注意：短信迁移属于推荐完整方案，若期限不足可降到 P2。不得牺牲主闭环去堆积额外场景。

## 5. 技术选型及理由

| 模块 | 主选 | 理由与替换边界 |
|---|---|---|
| 应用语言 | Python 3.10/3.11 兼容，优先 3.11 新环境 | 当前探针已在 3.10.8 运行；类型契约清晰 |
| 状态与契约 | LangChain Core + Pydantic + 显式状态机 | RunnableSequence 连接角色调用与合约校验，StructuredTool 提供只读图检索，状态和预算集中测试 |
| 算法 | scikit-learn Pipeline | 统一 fit/predict_proba，低资源，预处理与模型可组合 |
| 知识存储 | SQLite + nodes/edges 表 | 单机易复现，外键、事务、版本记录齐全 |
| 图计算与展示 | 有界图扩展 + NetworkX / D3 | KnowledgeStore 执行关系检索，NetworkX 提供 Python 图布局，D3 提供浏览器交互视图 |
| 文本检索 | 中文关键词归一化 + 字符 n-gram TF-IDF | 无额外模型即可检索中英混合能力描述；FTS5 作为可选实现 |
| LLM | OpenAI SDK Responses + DeepSeek HTTP + 本地 vLLM + Mock | 四种 Provider 共用结构化角色合约；模型服务与 CPU 算法验证分离 |
| API / CLI / UI | FastAPI / Typer / Vue，保留 Streamlit | 命令行、API 与主工作台共享业务层，Python 实验入口使用同一服务 |
| 代码执行 | 独立 Linux worker + Docker 资源隔离 | 生成代码不在应用进程中直接 import |
| 测试与规范 | pytest、Ruff、类型检查、CI | 对应 30% 代码质量评分，保留离线快速测试 |
| 报告 | JSON 为事实源，Jinja2 输出 HTML | 不让 LLM 编造指标；LLM 只解释确定性结果 |

LangChain 角色链与显式状态、审计事件和类型化工具共同执行任务。四卡扩容调整 Provider 与调度配置，算法插件、知识 schema 和验证器保持一致。实际工具职责、选择理由与运行方式见 [技术选型与框架集成](14_技术选型与框架集成.md)。

## 6. 分阶段实施与“过关”标准

| 工作日 | 工作内容 | 必须留下的验收证据 |
|---|---|---|
| D1 | 需求矩阵、数据卡、切分冻结、人工基线 | data manifest、哈希、baseline report、未使用最终测试集声明 |
| D2 | 核心 schema、能力来源抽取、SQLite 图 | 12–20 个可追溯能力记录，节点与关系导出，抽取小样本人工核对 |
| D3 | 统一算法接口、验证器、资源约束 | 人工模板通过验证；错误接口、泄漏列、超时等会正确失败 |
| D4 | LLM provider、TaskSpec、Planner、代码生成 | 真实 LLM 生成的一个候选完成独立验证，保存请求与代码哈希 |
| D5 | 修复闭环、候选比较、错误分类 | 真实失败和最多两轮补丁，失败终态按预算结束 |
| D6 | 知识回写、幂等、版本与失败经验 | 相同结果不重复写入；相近任务检索命中历史经验 |
| D7 | 多角色协作、Beam Search、消融准备 | 搜索树与候选预算；禁用某角色/图检索的对照配置 |
| D8 | API、CLI、UI、可视化与报告 | 四个可演示页面；API 状态和制品接口，报告可独立打开 |
| D9 | 单卡部署、provider 故障切换、多卡配置 | 7B/14B 候选模型预检、单卡实测；四卡配置静态验证 |
| D10 | 短信插件、组去重与迁移 | 不修改主状态机完成第二任务；新的评估配置能生效 |
| D11 | 实验矩阵、稳定性、消融与故障演练 | 汇总 CSV、未通过案例、原始 trace、资源与 token 消耗 |
| D12 | 新环境复现、演示、README、发布检查 | 复现日志、完整截图/录像、提交清单、可提交的 Git 仓库 |

若 D5 还没有稳定闭环，停止新界面和跨场景工作，先修 P0。若生成质量不足，先缩小可写代码范围、提升检索证据质量、改接口验证，再做模型升级。

## 7. 建议最终仓库结构

以下是实施目标，不表示目录中的模块已全部实现。

~~~text
src/capability_factory/
  contracts/           # TaskSpec, Capability, Plan, Artifact, VerificationReport
  ingestion/           # 文档切块、AST 元信息、来源校验
  knowledge/           # SQLite、迁移、图路径检索、版本
  agents/              # extract, plan, code, review, curate
  providers/           # mock、HTTP、endpoint router
  workflow/            # 显式状态机、重试、恢复、预算
  search/              # beam 与节点记录
  execution/           # sandbox client、runner、资源限制
  validation/          # 输入/接口/指标/稳定性/策略检查
  plugins/             # tabular_binary、text_binary、metrics
  reporting/           # JSON、HTML、图谱与方案解释
  api/                 # FastAPI
  cli.py
ui/
configs/               # 任务、模型、资源、实验配置
schemas/               # JSON Schema、SQL migrations
knowledge/             # 有出处的 seed 文档、能力 JSON
examples/              # 自然语言需求、验证通过的脱敏制品
tests/                 # 单元/集成/故障/端到端
scripts/               # 下载、doctor、离线实验、部署预检
deploy/                # worker 与推理服务分离的部署配置
docs/                  # 方案、数据卡、实测与提交指南
~~~
