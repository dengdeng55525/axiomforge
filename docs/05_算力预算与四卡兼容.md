# 算力、模型部署与四卡 RTX 4090D 方案

## 1. 结论和支持范围

AlgoForge 的推理后端有三种可选模式：

1. **DeepSeek API**：无需本地 GPU，适合最快完成端到端闭环和质量对照。
2. **本地 OpenAI 兼容 HTTP**：把 Qwen 等代码模型独立部署为 HTTP 服务，AlgoForge 通过
   `provider=local_http` 调用。
3. **Mock**：无密钥、无 GPU 的确定性离线模式，用于测试工作流和前端。

当前硬件目标是 **最多四张 RTX 4090D（每张 24 GB）**。四卡配置只描述可复现的
部署边界和预检命令；只有在目标机器上完成权重下载、服务启动、接口 smoke、并发、显存、
吞吐和故障恢复测试后，才能把它标记为已验证部署。配置文件不会自动下载模型，也不会在
启动 AlgoForge 时占用 GPU。

完成笔试闭环不需要训练大语言模型。银行表格和 SMS 文本算法默认在 CPU 受限 worker
中运行，GPU 只服务代码模型。应用、LLM 服务和算法 worker 彼此隔离：卡数只出现在
部署 profile 和调度层，业务代码不写死 `cuda:0`。

## 2. 四卡主机的资源档位

| 档位 | CPU | 主机内存 | GPU | 可用磁盘 | 用途 |
| --- | ---: | ---: | --- | ---: | --- |
| API 基础 | 4 核 | 8 GiB | 无 | 20 GiB | Mock/API 与单个 CPU 算法任务 |
| API 推荐 | 8 核 | 16 GiB | 无 | 50 GiB | Web、知识库和两个受限 worker |
| 单卡本地 | 8–16 核 | 32 GiB | 1×24 GB | 80 GiB | 7B/14B AWQ，一个本地端点 |
| 双卡本地 | 16 核 | 64 GiB | 2×24 GB | 150 GiB | 32B AWQ TP=2，或两个单卡副本 |
| 四卡本地 | 16–24 核 | 64–128 GiB | 4×24 GB | 250 GiB | 四个 14B 单卡副本，或 32B BF16 TP=4 |

这些是容量规划，模型加载、KV cache、编译、page cache、算法 worker
和前端都会消耗主机内存；容器的 `memory.max`、CPU quota、共享内存和临时磁盘应按实际
部署重新测量。四张卡合计 96 GB 显存需要通过张量并行、流水线并行或端点池进行调度，硬件显存保持独立。

## 3. 推荐的四卡 14B 形态

默认 profile 是 `four_gpu_14b`：四个
`Qwen/Qwen2.5-Coder-14B-Instruct-AWQ` 单卡副本，各绑定一张卡和一个本地端口。
这种形态不要求跨卡 tensor parallel 通信，适合将 Planner、Coder、Reviewer 和 Repair
任务放进统一队列，再按健康状态路由到端点：

```text
GPU 0 → coder14 → 127.0.0.1:8100/v1
GPU 1 → coder14 → 127.0.0.1:8101/v1
GPU 2 → coder14 → 127.0.0.1:8102/v1
GPU 3 → coder14 → 127.0.0.1:8103/v1
                         ↓
             AlgoForge local_http Provider
```

四副本的优势是任务级并发和故障摘除简单；它不会自动提高单个请求的上下文长度。
若更看重单请求质量，可以在四卡上自行配置 32B BF16 TP=4，但必须在目标驱动、CUDA、
vLLM 和模型 revision 固定后实测显存和通信；当前仓库没有把这条实验路线设为默认
profile。14B 单卡副本是本项目的默认验收路线。

## 4. 模型与显存估算

配置中的候选模型是固定 revision 的 Qwen2.5-Coder 7B/14B AWQ 和 32B AWQ/BF16。
它们是可替换的兼容基线，项目通过 OpenAI 兼容接口接入不同厂商。真正选型要在固定需求集上比较
结构化输出成功率、代码可运行率、修复成功率、延迟和资源峰值。

| 候选 | 起始方式 | 四卡建议 |
| --- | --- | --- |
| 7B AWQ | 单卡，8K 总上下文，`max_num_seqs=2` | 辅助角色或低延迟基线 |
| 14B AWQ | 单卡，16K 总上下文，`max_num_seqs=2` | 默认四卡副本，每卡一个端点 |
| 32B AWQ | TP=2，先用双卡 smoke | 需要两组时才启用，不能假设单卡稳定 |
| 32B BF16 | TP=4，短上下文、并发 1 起步 | 四卡单端点质量对照 |

权重显存的下界可按“参数量 × 每参数字节数”粗估，实际显存还包括量化元信息、未量化
层、KV cache、临时 workspace 和框架开销。KV cache 还会随上下文长度和并发序列线性增长。
`max_model_len` 是输入和输出总预算，配置时应先控制检索证据和输出长度，再
逐步增加上下文。任何 OOM 都要记录实际显存、主机内存、上下文、并发和模型 revision，
不能用理论容量代替实测。

## 5. 生成本地服务规划

规划器只读取 [inference_profiles.json](../configs/inference_profiles.json)，校验 GPU
分配、端口、tensor parallel 和模型 revision，然后打印命令：

```bash
.venv/bin/python scripts/plan_inference.py \
  --profile four_gpu_14b \
  --available-gpus 4
```

输出中的四个 vLLM 命令可以由部署者分别执行；也可以使用仓库提供的
`scripts/start_local_vllm.sh` 一次启动四个受控子进程。规划器自身不会拉取权重、启动服务、修改
`CUDA_VISIBLE_DEVICES` 或探测真实吞吐。服务应监听本机或受保护的私网地址，使用固定
`--served-model-name`（示例为 `coder14`），并在服务端开启鉴权；不要把未鉴权推理端口
暴露到公网。

部署前至少记录：

- `nvidia-smi`、驱动、CUDA、PyTorch、vLLM 和量化 kernel 版本；
- 模型和 tokenizer revision、许可证、权重缓存路径和 SHA；
- 每个端点的健康检查、首 token 延迟、吞吐、显存/RAM 峰值和并发上限；
- 单卡故障时的摘除、队列重试、超时和幂等 request id 行为。

算法 worker 应继续使用低权限、禁网和资源限制；不要因为本地模型需要 GPU/通信权限就
把生成代码 worker 改成 privileged 进程。

## 6. API、本地和 Mock 的切换

### DeepSeek API

在项目根目录创建未提交的 `.env`（可由 `.env.example` 复制）：

```dotenv
DEEPSEEK_API_KEY=your-key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash
```

检查端点并提交任务：

```bash
.venv/bin/python -m capability_factory doctor --check-api
.venv/bin/python -m capability_factory run \
  --dataset bank --provider deepseek --max-candidates 2 --max-repairs 2 \
  --description '预测银行客户订购定期存款，禁止 duration，报告验证集 AP。'
```

API 请求可能产生费用和网络失败；运行报告会记录 provider、实际 model、usage 和请求
哈希，密钥不会写入报告，也不会传给算法 worker。

### 本地 HTTP

本地服务准备完成后，将 `.env` 改为：

```dotenv
LOCAL_LLM_BASE_URL=http://127.0.0.1:8100/v1
LOCAL_LLM_ENDPOINTS=http://127.0.0.1:8100/v1,http://127.0.0.1:8101/v1,http://127.0.0.1:8102/v1,http://127.0.0.1:8103/v1
LOCAL_LLM_MODEL=coder14
LOCAL_LLM_PROFILE=four_gpu_14b
```

四卡脚本使用 `coder14` 作为四个端点共享的 served model name；如果自行修改
`--served-model-name`，必须同步修改 `LOCAL_LLM_MODEL`：

```dotenv
LOCAL_LLM_MODEL=coder14
LOCAL_LLM_API_KEY=
```

在已安装 vLLM、CUDA 和匹配驱动的 GPU 主机上启动服务：

```bash
# 只需首次执行；安装到项目 .venv，不影响系统 Python。
./scripts/install_local_vllm.sh

LOCAL_LLM_PROFILE=four_gpu_14b \
  LOCAL_LLM_AVAILABLE_GPUS=4 \
  ./scripts/start_local_vllm.sh
```

启动脚本会自动使用 `.venv/bin/vllm`，不要求先激活虚拟环境。首次启动还会从
Hugging Face 下载约 10 GB 的 14B AWQ 权重，四个端点共享本机缓存，后续启动不再重复
下载。若网络环境设置了 `socks5://` 代理，安装脚本已包含 `socksio`；若目标网络允许直连，
可以清除代理变量后启动：

```bash
env -u ALL_PROXY -u HTTP_PROXY -u HTTPS_PROXY \
    -u all_proxy -u http_proxy -u https_proxy \
    LOCAL_LLM_PROFILE=four_gpu_14b \
    LOCAL_LLM_AVAILABLE_GPUS=4 \
    ./scripts/start_local_vllm.sh
```

直连无法访问 Hugging Face 时保留代理即可；这只影响权重下载，不影响 AlgoForge 的
DeepSeek API 配置。单卡首次验收可用 `LOCAL_LLM_PROFILE=single_gpu_14b
LOCAL_LLM_AVAILABLE_GPUS=1`，它使用相同的 `coder14` 服务别名和 8100 端口。

服务启动后，再把命令中的 provider 换成 `local_http`：

```bash
.venv/bin/python -m capability_factory run \
  --dataset bank --provider local_http --max-candidates 2 --max-repairs 2 \
  --description '预测银行客户订购定期存款，禁止 duration，报告验证集 AP。'
```

Provider 只连接配置的 OpenAI 兼容端点，不读取或转发 `DEEPSEEK_API_KEY`。若服务别名、
端口或模型 revision 改变，必须同步配置并重新做结构化输出、代码验证、质量、并发和
OOM 检查；不能把 API 的延迟或质量结论直接套到本地模型。

### Mock 离线模式

```bash
.venv/bin/python -m capability_factory init --provider mock
.venv/bin/python -m capability_factory run \
  --dataset bank --provider mock --max-candidates 2 --max-repairs 2 \
  --description '验证银行营销响应预测闭环。'
```

Mock 不调用模型，但仍会执行真实的数据处理、受限代码验证、指标计算和知识回写，适合
CI、前端联调和没有 GPU/API 凭证的环境。Mock 结果不能作为真实模型质量结论。

## 7. 调度、预算和安全边界

每个本地端点都应有并发 semaphore、队列上限、超时、熔断和健康状态；失败重试必须带
幂等 ID，避免模型服务或工作流重试风暴。算法候选仍受 CPU/RAM 配额限制，GPU 数量不
等于可以无限增加 Python worker。

API 和本地模型都使用同一套任务协议、验证器、报告和知识回写，因此可以先用 Mock 验证
流程，再用 API 做质量基线，最后在四卡本地端点做成本、延迟和隐私对照。报告必须标出
`provider`、`mode`、实际模型、版本、资源观测和未完成检查；没有观测的数据保持“未记录”。

## 8. 四卡验收清单

1. 先运行 `api`/Mock 和单卡本地 smoke，确认结构化输出、代码编译和算法验证。
2. 按 GPU 0→3 逐个启动 14B 端点，确认健康检查、别名和端口唯一。
3. 逐步升到四端点并发，记录首 token、吞吐、显存、主机内存、队列等待和错误率。
4. 人为摘除一个端点，确认任务只重试到健康端点，失败证据仍写入报告和知识库。
5. 用同一需求集比较 API、Mock 和本地 provider；指标、验证协议和报告字段保持一致。
6. 将命令、版本、模型 revision、硬件、结果和限制写入 `docs/research/*validation.json`。

本仓库目前提供四卡静态规划和 provider 接口；本地权重、vLLM 服务、四卡吞吐和 OOM
恢复只有在目标机器执行并保存证据后，才可从“计划”升级为“已验证”。
### 当前 CUDA 兼容启动默认

项目启动器默认使用 `--enforce-eager`，并设置
`VLLM_USE_FLASHINFER_SAMPLER=0`。前者关闭 vLLM 的 CUDA Graph/编译预热，
后者避免系统 CUDA 11.8 在首次构建 FlashInfer 采样扩展时使用不兼容的
CUDA 13 编译参数。Qwen AWQ 模型仍在 GPU 上执行；确认升级驱动、CUDA
工具链与 FlashInfer 后，可显式设置 `VLLM_USE_FLASHINFER_SAMPLER=1`
进行性能对比。
