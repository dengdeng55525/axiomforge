# 统一验证、实验设计与答辩展示

## 1. 验证的五个层次

| 层次 | 核心检查 | 失败处理 |
|---|---|---|
| 安全与策略 | 无越权读写/网络、依赖白名单、禁用特征、标签隔离 | 阻断发布，分类记录，禁止通过放宽策略“修好” |
| 接口与功能 | 可导入、fit/predict_proba、正类映射、行对齐、概率有效 | 返回结构化失败证据，允许有限修复 |
| 指标与业务 | AP、ROC-AUC、F1、前 10% 名单效果、相对基线 | 标记质量门槛是否达成；保留失败结果，不伪造通过 |
| 稳定性与边界 | 缺列、额外列、未知类别、空批次、单行、重复请求 | 支持的边界需正确处理；不支持的输入需明确报错 |
| 资源与复现 | 时间、峰值 RSS、CPU、退出码、依赖、种子、制品哈希 | 超预算终止，重复运行比较与差异报告 |

质量好但安全/接口失败的候选不进入最终候选；安全通过但指标低的候选仍可作为诊断材料。report.status 与 quality_status 分开，不用一个含糊的“成功”覆盖所有状态。

## 2. 指标定义与冻结协议

主排序指标使用 sklearn.metrics.average_precision_score，报告名明确写 AP。AP 与对 PR 曲线做梯形积分的数值不总是相同，不混用“PR-AUC”标签。

辅助指标：ROC-AUC、正类 precision/recall/F1、混淆矩阵、Brier score（若声称概率可用）、Precision@10%、Recall@10%、Lift@10%。

业务名单公式：k = ceil(0.1 × N)；按 score 降序、row_id 升序稳定排序。Precision@10% = 前 k 条正类数 / k；Recall@10% = 前 k 条正类数 / 全部正类数；Lift@10% = Precision@10% / 本集合正类比例。常数分数具有大量并列，要明确排序规则和随机基线的期望，不能把偶然次序当预测能力。

阈值 0.5 需要通过验证集实验确认。本次银行人工基线在此阈值下 F1 为 0，报告完整保留该结果。实施阶段应根据明确目标选择阈值或使用固定联系预算排序，并将策略冻结到制品。训练后概率校准使用训练区内部独立校准集或合适的交叉验证，最终测试集保持封存。

质量门槛在最终测试前冻结，建议分层：

- 系统硬门槛：所有接口/安全/策略检查通过。
- 算法底线：验证 AP 超过同协议 Dummy 基线；最终模型至少接近同协议人工参考算法，容许差值建议 0.01 AP，需在预注册配置中写明。
- 进阶目标：在固定预算下，比较搜索/修复对合格运行率和最优 AP 的影响，并报告与人工模型的差异。
- 最终测试若未达门槛，如实标记泛化不足并分析原因；不得在测试集上迭代直到“达标”。

不预设“必须 AUC≥0.9”这类与业务可用字段和时间划分无关的承诺。

## 3. 当前真实可行性结果

以下均为手写基线，在验证集实测；它们用于提供 CPU 参考值。种子 42，Python 3.10.8，scikit-learn 1.7.2。

| 任务/候选 | AP | ROC-AUC | F1@0.5 | 训练秒数 | 进程峰值 RSS MiB |
|---|---:|---:|---:|---:|---:|
| Bank Dummy | 0.1107 | 0.5000 | 0.0000 | 0.037 | 164.1 |
| Bank LogisticRegression | 0.1829 | 0.6131 | 0.0000 | 0.053 | 165.0 |
| Bank RandomForest | 0.1398 | 0.5718 | 0.0000 | 1.737 | 171.8 |
| SMS Dummy | 0.1250 | 0.5000 | 0.0000 | 0.094 | 157.0 |
| SMS TF-IDF + LogisticRegression | 0.9584 | 0.9881 | 0.8056 | 0.104 | 159.0 |
| SMS TF-IDF + ComplementNB | 0.9459 | 0.9781 | 0.9024 | 0.094 | 158.0 |

原始结果、完整特征协议和划分见 research/baseline_results.json。耗时从 fit 调用计时，RSS 是每个独立进程的 Linux ru_maxrss，不包含 LLM 服务、容器启动或所有子进程总和。这个小样本实测证明 CPU 算法可行，不能据此承诺整次 Agent 请求在一秒内完成。

结果说明方案比较的必要性：主场景中树模型与线性模型各有表现，短信 AP 最优模型与固定阈值 F1 最优模型可能不同。

## 4. 系统级实验矩阵

准备固定 12 条需求（8 条银行、4 条短信），其中包括正常请求、资源限制、未知类别、不同指标和不可满足约束。提示词、来源清单、模型 revision、split、预算在实验前冻结。

比较以下配置：

| 编号 | 配置 | 要回答的问题 |
|---|---|---|
| A | 单次代码生成、无检索、无修复 | 最简单起点能成功多少？ |
| B | 文本检索 + 生成、无图路径 | 文本知识是否有效？ |
| C | 图约束检索 + 生成 + 有限修复 | 图关系与修复是否帮助？ |
| D | C + 多角色 + Beam Search | 在同预算下是否值得额外协调？ |

每种配置对同一 12 条需求运行三次，合计 144 个系统 run。开发 smoke 先跑每种配置三条需求一次，完整规模按实验计划逐步执行。

公平性：固定最大总 token、候选次数、wall time 和模型；同时报告成功率与实际花费。多角色允许内部多次调用，但不能隐藏其更高成本。补充“相同总预算”和“各自自然开销”两种比较，说明哪个结论适用于哪种口径。

核心汇总字段：首次可运行率、预算内最终合格率、条件修复成功率、AP 相对 Dummy/人工基线变化、平均/p95 延迟、输入/输出 token、峰值资源、拒绝原因、人工干预次数、经验复用命中率。

同一任务的多次运行相关，不把 144 次当成 144 个完全独立任务。按任务聚合或 cluster bootstrap 给区间；样本小时用描述性结果，不宣称普遍显著优势。记录超时与失败分母，禁止只汇总成功样本。

## 5. 安全与错误注入试验

最少六种真实 fixture：未知类别报错、类别概率列反转、缺少必需接口、读取禁用 duration、稀疏/稠密不兼容、无限循环或超时。故障注入必须标明 injected=true；其成功率与自然生成错误的修复率分别报告。

额外用例：非法网络请求、路径逃逸、读取环境密钥、输出超大文件、恶意反序列化、从外部文档注入“忽略系统约束”、篡改验证脚本。测试的判定标准是隔离/拒绝是否正确，不需要执行造成真实破坏的样例。

每次修复保存 before_hash、error_type、diagnosis、patch_hash、checks_before/after、new_metrics、budget_used。经验条目附上失败指纹、有效补丁和适用环境，后续用另一个相似任务验证能否避免复发。

## 6. 图谱与能力抽取评估

用人工标注的小集合评估字段完整率、约束正确率、关系 precision/recall、有效出处比例。用 10 条固定检索问题评估 top-5 是否包含所需能力和关键禁用约束。报告标注人数及规模，单人复核不冒称专家双盲评测。

“图有多少节点”属于规模指标。核心效果应展示图路径召回历史失败经验后对计划或生成代码的影响，并提供消融对照。

## 7. 资源扩展实验

单卡与四卡必须区分两类实验：

- 同模型、同量化、同长度、同预算，增加独立副本：比较吞吐、p95、队列等待和每次成功成本。
- 更换模型大小或量化：比较生成质量与成本；不能把质量变化全部归因于多卡。

固定任务集和 2K/8K 输入长度档，记录模型预热，单请求和 2/4 并发，完成率、OOM、GPU memory/utilization、host RAM、CPU、TTFT、输出速度、端到端 run/s。TTFT 和每 token 速度不得用算法训练耗时代替。

先单卡预检，再每次扩一个组；四卡到位前只能完成配置与静态测试，真实吞吐和多卡兼容性应标记 pending。

## 8. 报告模板

每份报告包含：运行身份与模式；需求与显式假设；数据/特征/切分版本；证据路径；计划与候选；生成代码和依赖哈希；检查结果；验证指标与参考基线；阈值/联系预算；修复记录；资源开销；风险与局限；知识回写 ID；复现命令。

报告指标来自不可篡改的结果对象；解释文本引用字段，不让 LLM 自由编数字。离线回放显示 replay，mock 显示 mock；提交的主示例至少一个来自真实 LLM。

## 9. 建议 8–10 分钟演示

1. 0–1 分钟：讲业务目标、数据来源和 duration 限制。
2. 1–3 分钟：提交需求，展示结构化约束和可追溯图路径。
3. 3–5 分钟：展示生成代码、两个候选、统一验证和一次有限修复。
4. 5–6 分钟：展示能力新版本和第二次任务命中的失败经验。
5. 6–7 分钟：同一引擎运行短信插件，说明变更点。
6. 7–9 分钟：消融表、资源实测、单卡到四卡部署设计、诚实局限。
7. 最后一分钟：展示全新环境复现命令、测试结果和 Git 提交。

现场优先使用一个短的真实调用；耗时实验展示已保存、可校验的完整 trace 与录像。网络失败时切到明确标记的回放，避免把录制内容当作实时执行。

## 10. 常见追问的准备

- 为什么用图？回答一个实际改变计划的关系路径及消融结果。
- 与 AutoML 有什么区别？解释语言约束理解、来源抽取、代码生成/修复、验证与经验沉淀。
- 为什么采用角色化编排？展示不同角色的协议、独立审查和可关闭的角色。
- 怎样防止模型作弊？展示标签隔离、固定 evaluator、制品哈希和禁用字段检查。
- GPU 多了有什么提升？区分推理容量、实验吞吐、模型质量，给出实测而非线性加速承诺。
- 哪些还没完成？以状态表和证据为准，清楚区分设计、静态验证、单卡实测和四卡待测。
