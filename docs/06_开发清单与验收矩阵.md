# 开发任务、评分证据与交付检查

## 1. 评分投入

题面权重：技术能力 40%、代码质量 30%、创新性 15%、完整性 15%。下面是证据映射，不是自称取得的分数。

| 评分维度 | 最有说服力的实现 | 必须提交的证据 |
|---|---|---|
| 技术 40% | 真实抽取/检索/规划/生成/修复/回写；统一 evaluator | 一个真实 LLM 完整 run、数据与模型来源、schema、trace、失败修复 |
| 质量 30% | 模块职责、契约、错误处理、预算、测试、依赖锁定 | pytest/lint/类型检查结果、CI、干净环境复现日志 |
| 创新 15% | 有验证支撑的图检索、失败经验和预算内 Beam | 消融、真实搜索树、后续任务复用经验的记录 |
| 完整 15% | 文档齐全、简洁 UI/CLI、示例与报告可重放 | README 十项要求、报告、截图/录像、GitHub 仓库 |

不要将大模型参数量、GPU 数量、界面动画或无边界的自动化当作高分保证。实现的可检查性比口号更重要。

## 5. 测试范围

P0 单测覆盖：schema、输入/类别映射、未知类别、禁用字段、正类概率列、行对齐、指标方向、图关系、版本和幂等、预算、状态转换。

集成测试覆盖：mock 离线闭环、真实 API 可选 smoke、知识摄取→检索、生成→runner→report、失败→修复→回写、取消任务→资源释放。

安全与资源测试覆盖：无网、目录隔离、不能读 key/test labels、超时、OOM、进程上限、输出大小限制、错误依赖。实际执行隔离测试需要可用 Linux sandbox；缺少时跳过并标明原因，不算通过。

代码质量目标：关键 contracts/workflow/validation/knowledge 模块 line coverage ≥80% 是内部目标；同时检查有意义的分支覆盖与变异错误能否被发现，不为了数字编写复述实现的测试。

CI 快速链路应不要求 GPU、不依赖收费 API；端到端真实 LLM 与 GPU tests 使用显式标记按需运行。机密不写测试报告。慢测试、模型缓存和网络访问有独立配置。

## 6. Git 工作约定

初始仓库 main 分支已经创建。提交按可验收功能组织，例如 feat(knowledge)、feat(workflow)、feat(validation)、test(repair)、docs(report)。每个重大里程碑至少一次清晰提交，不把全部工作堆成 final version。

.env、模型权重、原始数据、SQLite 运行库和大日志不入库；提交小型脱敏报告和来源 manifest。发布前检查大文件、密钥和虚假示例结果。

本次无既有 Git 作者配置时，只在本仓库使用 Project Bootstrap / bootstrap@localhost 作为初始化身份，没有替用户虚构个人邮箱。正式发布前可设置真实作者身份；无需为了调整身份改写已有历史。

本次没有创建远程 GitHub 仓库或推送。最终实现完成后，由用户指定仓库/账号或使用其已授权凭据完成远程提交；不要自动把公开数据以外的材料发布到未知地址。
