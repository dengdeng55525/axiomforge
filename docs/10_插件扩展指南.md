# 受信任指标与参考代码模板扩展

本项目提供小型、可测试的进程内插件注册表，满足原题“支持插件式接入新的算法模板或评估指标”的进阶要求。实现位于 src/capability_factory/plugins.py，无新增第三方依赖。

当前扩展范围是**已有二分类任务的指标和参考代码模板**。它不注册新行业数据集，不自动增加新的分类器，也不放宽 AST 构造器白名单。开发者若要增加全新任务或算法，仍须单独修改并验证任务契约、计划契约、数据协议和执行器策略。

## 1. 注册边界

插件由可信应用开发者在进程启动阶段显式注册。框架不扫描插件目录、不加载 entry points、不根据自然语言或请求参数 import 模块，也不执行模型输出中的插件注册代码。

可信指标 callable 在宿主机进程中运行，属于应用代码，**不是沙箱中的不受信任代码**。不要把用户上传的 Python 函数、模型生成的代码或未经审阅的第三方函数注册进去。

注册表使用 RLock 保护，每次计算复制当时的注册项，再释放锁执行 callable。计算期间的新注册项只影响下一次调用。不同服务进程不共享内存注册表，多 worker 部署应在每个可信进程内执行相同初始化。

## 2. 指标接口

    register_metric(name, function) -> None
    evaluate_metrics(labels, scores) -> dict[str, float]

function 接收两个只读序列：二值标签和对应正类概率；返回一个有限实数。宿主可信验证器先执行原有行对齐、正类和概率范围检查，再调用插件。插件本身可增加额外适用条件检查。

命名采用 1–48 位小写字母、数字和下划线，首位必须是字母。结果统一加入 plugin_ 前缀，例如注册 brier_loss 后返回 plugin_brier_loss，不能覆盖 average_precision、roc_auc 或已有验证字段。

最小示例：

    from capability_factory.plugins import register_metric, evaluate_metrics, brier_loss

    register_metric("brier_loss", brier_loss)
    result = evaluate_metrics([0, 1], [0.1, 0.8])
    assert abs(result["plugin_brier_loss"] - 0.025) < 1e-12

也可以在可信启动阶段显式调用：

    from capability_factory.plugins import register_builtin_examples
    register_builtin_examples()

它只注册可选 Brier loss 示例；模块 import 本身不自动注册。重复注册同名指标会抛出 PluginError，即使传入同一个函数也不静默覆盖。因此每个进程只调用一次对应初始化，不在每个 HTTP 请求中重复注册。

Brier loss 是正类概率与二值标签之间的均方误差，越低越好。它是补充观察指标，不改变本项目预先指定的 Average Precision 主选型规则。示例实现检查非空、长度一致、二值标签和有限的 [0,1] 概率。

### 失败行为

- NaN、正负无穷、字符串、数组、布尔值、复数等不合法输出会抛出 PluginError。
- callable 抛异常时，错误会带插件名和原始异常类型，不能用 0 或缺省“成功”掩盖。
- 传入 callable 的标签和分数是 tuple 快照，插件不能通过修改列表破坏原指标输入。
- 不返回部分计算结果来伪装整组指标成功；调用方按既有失败记录机制处理异常。

注册表只验证插件的结构与数值输出，不证明其数学定义正确。新增指标需要相应已知答案测试，并明确适用任务、单位、方向和解释。

## 3. 参考代码模板接口

    register_template(task_type, algorithm, function) -> None
    get_reference_code(task_type, algorithm, variant="default") -> str

function 的签名为：

    function(task_type: str, algorithm: str, variant: str) -> str

注册键是任务类型与算法 ID 的二元组。没有覆盖项时，get_reference_code 延迟调用已有 execution.reference.reference_code，保持原有参考实现。

当前接受的规范任务类型：

- tabular_binary_classification
- text_binary_classification

当前算法 ID：logistic、forest、extra_trees、nb、dummy。nb 参考模板仅适用于文本任务。这些是现有 CandidatePlan 范围；注册表不能使 xgboost 或任意其他分类器自动进入执行器。

调整已有逻辑回归模板的示例：

    from capability_factory.execution.reference import reference_code
    from capability_factory.plugins import register_template, get_reference_code

    def smaller_logistic(task_type, algorithm, variant):
        source = reference_code(task_type, algorithm, variant)
        return source.replace("max_iter=1000", "max_iter=500")

    register_template("tabular_binary_classification", "logistic", smaller_logistic)
    source = get_reference_code(
        "tabular_binary_classification", "logistic", "regularized"
    )

这个示例保留原有预处理、随机种子和模型接口，只调整受控参数。生产开发中也可以返回维护良好的完整模板。模板输出必须是非空字符串；同一注册键重复注册会报错。

## 4. 模板注册不授予执行许可

get_reference_code 只选择并返回源文本，**不表示代码已获执行批准**。参考代码和由 LLM 生成／修复的代码仍须通过独立的：

1. AST 语法与导入白名单检查。
2. 构造器、参数范围及资源策略检查。
3. 实际分类器与计划算法的一致性检查。
4. 数据协议、接口、预测输出和可信指标验证。

测试中既包含“修改后的合法模板确实通过注册表并到达 AST 分析”，也包含“注册了含不允许导入的模板，独立编译器仍然拒绝”。不要在 registry 内调用 exec，也不要根据模板字符串动态 import 插件。

## 5. 宿主集成位置

- 可信二分类指标函数在完成原有验证和核心指标后，调用 evaluate_metrics 并合并 plugin_ 命名空间下的结果。
- 工作流生成提示所使用的参考代码，通过 get_reference_code 获取；未注册模板时继续使用既有实现。
- 注册项必须在接受任务前由可信初始化代码添加，不能根据请求里的模块名、代码段或任意文件路径添加。
- 指标插件只收到验证所需的标签和概率，不改变封存测试集访问纪律；是否进行最终测试仍由独立发布评估流程控制。

## 6. 测试与已知边界

执行：

    .venv/bin/pytest tests/test_plugins.py -q

当前 **27 项测试通过**，覆盖已知 Brier 数值、命名空间、重复注册、非数值和非有限输出、异常传播、注册表快照、输入不可变、并发注册、原模板回退、合法模板改写、独立 AST 拒绝、任务／算法范围和参数校验。

此实现是显式、可信、进程内扩展机制，不是任意用户代码插件平台。插件版本和发布审查目前由 Git 与应用依赖锁管理；不提供远程安装、热卸载或跨进程注册广播。
