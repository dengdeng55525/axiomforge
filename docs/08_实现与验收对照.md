# 实现与验收对照

本表逐项对应 [笔试原题](source/exam.txt)，依据实际代码与制品编写；设计目标与已完成项分开记录。记录日期：2026-09-30；提交历史以当前仓库 Git 记录为准。

**已实现**表示有代码入口；**有真实示例**表示保存了对应运行；**部分实现**表示存在明确边界；**待验收**表示仍需完成独立验证。最终测试数量、运行 ID、制品哈希、通过/失败分布，以 `docs/research/execution_validation.json` 为权威验收索引；没有记录不能算通过。本表不承诺考试分数。

## 3. a–g 闭环逐步取证

| 步骤 | 代码与事实字段 | 复核要点 |
|---|---|---|
| a 理解能力描述 | interpreter、TaskInterpretation、report.interpretation | 需求与固定 task_spec 一起输入，记录假设及不兼容请求 |
| b 检索知识 | KnowledgeStore.search、report.evidence | 固定来源、能力 ID、locator、文本/图分数与 evidence_path 可追踪 |
| c 规划算法 | planner、CandidatePlan、candidate.plan | 算法和候选 ID 合法，引用来自实际检索，不能凭空创造来源 |
| d 生成代码 | coder/repair_coder、GeneratedCode、candidate.attempts | 保存每次代码、解释与 SHA256，代码只实现 build_pipeline |
| e 自动执行验证 | compile_constructors、validate_candidate、verification 文件 | 由可信代码训练和评估，模型不能自己填写通过或指标 |
| f 错误修复/优化 | reviewer、repairs、before_hash/after_hash | 最多两次修复，受预算/接口限制，明确注入与自然错误 |
| g 结果沉淀 | save_run、record_experience、knowledge_writeback | 成功/失败/取消保留；能力版本、来源、尝试制品和修复关系可查 |

优先展示同一 run_id 的整条链，不用不同运行的漂亮截图拼成一条假闭环。修复经验的验证状态应关联到真实通过的补丁/尝试，不能以“最终有一个候选成功”替代每条经验的验证。

## 8. 演示命令与实验口径

完整安装和说明见 [07 指南](07_使用与演示指南.md)。以下在项目根目录、已安装依赖并配置后端 API 的环境中运行：

~~~bash
python -m capability_factory init --provider deepseek
python -m capability_factory run --dataset bank --provider deepseek \
  --description '构建通话前银行营销响应预测，禁止 duration，比较两个候选。' \
  --max-candidates 2 --max-repairs 2 --inject-failure
python -m capability_factory run --dataset bank --provider deepseek \
  --description '依据知识图和失败经验搜索银行营销响应预测方案。' \
  --search beam --max-candidates 6 --max-repairs 2
python -m capability_factory run --dataset sms --provider deepseek \
  --description '构建短信垃圾信息概率分类，比较两个候选并报告独立验证结果。'
python -m capability_factory export-graph --output artifacts/graph.json
python -m pytest tests ui -q
~~~

这些命令会生成新的 ID；注入故障实验保留 injected 标记。不能期待模型每次生成逐字相同代码，复核应使用记录的版本、来源、预算、提示和哈希。

~~~bash
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 --dry-run
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 \
  --profiles A,B,C,D --case-ids B01,S01 --output artifacts/experiments/mock-smoke
~~~

默认 smoke 是两条需求 × 四配置，每轮 8 次；full 是 12 条 × 四配置，每轮 48 次，三轮为 144 次。筛选配置/任务或修改 repeats 后按 dry-run 实际任务表计算，不能继续沿用默认数量。

A/B/C/D 的实际配置以运行器和输出 manifest 为准。当前 --no-use-graph 关闭图加分，不必然关闭全部文本检索；对照组名称必须反映真实机制，不能把仍有文本检索的配置称作“无检索”。报告实际候选/调用/token/耗时预算，不把不同开销的组直接包装成严格等预算结论。

## 10. 评分维度与剩余工作

| 维度 | 题面占比 | 最有力的验收证据 | 不应采用的替代品 |
|---|---|---|---|
| 技术能力 | 40% | 同一真实 run 的完整闭环、schema、固定验证和修复 | 一张界面图或只读设计文档 |
| 代码质量 | 30% | 模块合约、异常/取消/预算测试、依赖和复现 | 只说代码很多、只跑一个成功用例 |
| 创新性 | 15% | 图路径影响计划的案例、Beam/角色消融、经验复用 | 节点数量、角色名称或调用次数 |
| 完整性 | 15% | 安装入口、公开代码/报告、清楚限制和提交仓库 | 隐去失败、预填漂亮指标 |

提交前仍需明确核验以下事项，未出现在最终索引中的项目保持待验收：

1. 最新代码完整回归、API 队列/取消/超时、真实银行/短信/Beam 示例和公开副本完整性。
2. 完整依赖锁与独立净环境安装；当前主机跑通不能替代另一台机器复现。
3. 按真实调用预算执行更大规模 A/B/C/D；144 次完整矩阵不能因为脚本存在就标为完成。
4. 抽取 gold 的真实预测评测、图检索命中与独立经验复用实验；precision/recall 以专项评测结果记录。
5. 最终测试协议冻结后的一次性评估；当前开发报告只给验证集成绩。
6. 若用于公网，增加认证/租户隔离和真正 OS 沙箱；当前只交本地受控原型。
7. 本地大模型下载/部署及 1–4 卡通信、OOM、吞吐和回收；全部属于未来兼容验证。
8. 发布前检查仓库可见性、许可证、公开样例和敏感文件排除；当前代码已推送到所有者仓库，
   仓库按公开发布要求准备，代码许可证为 MIT；发布前检查可见性、许可证、公开样例和敏感文件排除。

这里的“剩余”用于区分代码存在、单次成功、系统性优势和生产可用等验收层级。以真实、可复核的证据获得评分，最终评价以评审结果为准。
