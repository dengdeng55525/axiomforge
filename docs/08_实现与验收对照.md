## 3. a–g 闭环逐步取证

| 步骤 | 代码与事实字段 | 复核要点 |
|---|---|---|
| a 理解能力描述 | interpreter、TaskInterpretation、report.interpretation | 需求与固定 task_spec 一起输入，记录假设及不兼容请求 |
| b 检索知识 | LangChain StructuredTool `search_capabilities`、KnowledgeStore.search、report.evidence | 固定来源、能力 ID、locator、文本/图分数与 evidence_path 可追踪 |
| c 规划算法 | planner、CandidatePlan、candidate.plan | 校验算法、候选 ID 与知识引用，引用指向本次实际检索结果 |
| d 生成代码 | coder/repair_coder、GeneratedCode、candidate.attempts | 保存每次代码、解释与 SHA256，代码只实现 build_pipeline |
| e 自动执行验证 | compile_constructors、validate_candidate、verification 文件 | 由可信代码训练、计算指标并生成检查结论 |
| f 错误修复/优化 | reviewer、repairs、before_hash/after_hash | 最多两次修复，受预算/接口限制，明确注入与自然错误 |
| g 结果沉淀 | save_run、record_experience、knowledge_writeback | 成功/失败/取消保留；能力版本、来源、尝试制品和修复关系可查 |

演示围绕同一 run_id 展开，依次检查需求、规划、生成代码、验证、修复与回写。每条经验关联到对应修复尝试及验证结果，保持经验状态与执行证据一致。

## 8. 演示命令与实验口径

完整安装和说明见 [07 指南](07_使用与演示指南.md)。以下在项目根目录、已安装依赖并配置后端 API 的环境中运行：

~~~bash
python -m capability_factory init --provider deepseek
python -m capability_factory run --dataset bank --provider deepseek \
  --description '构建通话前银行营销响应预测，禁止 duration，比较两个候选。' \
  --max-candidates 2 --max-repairs 2 --inject-failure
python -m capability_factory run --dataset bank --provider deepseek \
  --description '依据知识图和失败经验搜索银行营销响应预测方案。' \
  --search beam --max-candidates 6 --max-repairs 2
python -m capability_factory run --dataset sms --provider deepseek \
  --description '构建短信垃圾信息概率分类，比较两个候选并报告独立验证结果。'
python -m capability_factory export-graph --output artifacts/graph.json
python -m pytest tests ui -q
~~~

这些命令生成新的运行 ID；注入故障实验保留 injected 标记。复核按版本、来源、预算、提示和代码哈希定位具体运行，模型生成差异保留在各次报告中。

~~~bash
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 --dry-run
python scripts/run_experiments.py --provider mock --suite smoke --repeats 1 \
  --profiles A,B,C,D --case-ids B01,S01 --output artifacts/experiments/mock-smoke
~~~

默认 smoke 是两条需求 × 四配置，每轮 8 次；full 是 12 条 × 四配置，每轮 48 次，三轮为 144 次。筛选配置、任务或修改 repeats 后，dry-run 会给出对应的实际任务表与运行数量。

A/B/C/D 的配置由运行器和输出 manifest 记录。--no-use-graph 控制图关系加分，文本检索由对应检索配置管理。比较时核对每组的候选数量、调用次数、token 与耗时预算，并按实际启用机制解释结果。

### 交付复核

1. 检查当前提交的 CPU / Web CI，按 README 安装并运行示例。
2. 查看银行、短信、Beam 与修复报告，对照候选代码、接口检查、指标和知识回写。
3. 按 manifest 核验公开制品哈希，检查模式标签、数据来源、许可证和敏感信息排除。
4. 按使用环境选择 API 或本地模型，模型服务记录见 [本地部署实测](research/local_vllm_validation.json)，本地端到端记录见 [短信报告](../examples/evidence/sms_local_resources/report.json)。

### 扩展评测与部署路线

- **协作与复用评测**：用 A/B/C/D 配置、多次重复和固定预算评估角色协作、图检索及经验复用的收益。
- **知识抽取评测**：建立标注集，单独记录抽取 precision / recall、来源匹配和图检索命中率。
- **最终算法评测**：冻结方案与协议后执行封存测试集评估，保留独立于候选选择的最终结果。
- **服务运行评测**：在现有本地模型部署基础上增加持续吞吐、OOM、故障恢复和多卡负载实验。
- **部署扩展**：面向公网与多用户场景完善认证、租户隔离、持久队列和 OS 级执行隔离。
